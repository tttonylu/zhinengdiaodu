## 1. 转帖完整链路现状（已读真实代码）

发布链路（`unified-scheduler/repost/repost-engine.js` → `repostTweet()`）：

1. `extractTweetId` / `hasVideo` / `hasPhoto` / `isJapaneseTweet`（仅日语帖）过滤。
2. `stripMentions(extractTweetText(article), sourceHandle)` 生成正文，再 `finalText = cleanTxt + appendLink`，硬规则 `finalText.replace(/@\w+/g,'')`。
3. 媒体闸门 → 下载图片 blob。
4. 强关残留 compose → `humanClick(composeBtn)` → `waitFor('[data-testid="tweetTextarea_0"]')` 取编辑器。
5. `insertEditorText(editor, finalText)` 写入正文（四层兜底）。
6. 上传图片（fileInput + DataTransfer）。
7. `scrubEditorMentions` 二次清 @ → 找发送钮 `humanClick(postBtn)`。
8. 成功确认：编辑器消失 / toast / URL 跳转 三信号 + 「Something went wrong」重试 3 次 + 反垃圾冷却兜底。

输入写入 `insertEditorText` 四层：
- 层1 `EngineUtils.typeTextHumanLike`（拟人键盘 → execCommand insertText）
- 层2 `execCommand('selectAll')+delete` → `selectAll`+`insertText`
- 层3 合成 `paste`（ClipboardEvent + DataTransfer）
- 层4 合成 `beforeinput`/`input` / `textContent` 兜底

每层后 `looksOk(read())` 校验。

## 2. 逐环节复盘

### 2.1 19:00 开跑 —— 正确 ✅

链路逐跳验证通过：
- 迁移 `062_repost_start_1900.sql` 写入 `repost_follow_work_end='false'`、`repost_start_hour='19'`、`repost_start_min='0'`。
- `config-sync.js` `truthy('false', true)` **正确返回 false**（`v==='false'` 命中 `return false`）→ `followWorkEnd=false`；`pi('19',6)=19`。
- `repost-tracker.js getStartHm()`：`follow===false` 时走 `cfgStartHm()` 返回 `{h:19, m:0}`。
- `isPastStartClock()`：`startM=1140` > `workStartM=420`，19:00+jitter 后 `nowM>=effectiveStartM` 为真 → 19:00 开跑成立，且白天不会误拉起。

**无错位。** 唯一提醒：19:00 生效前提是迁移已随 `docker compose build && up -d --force-recreate` 落库；若 DB 已跑过迁移但因部署未执行则仍是旧值（不属于逻辑错误）。

### 2.2 发文输入核心方向 —— 正确 ✅

旧 bug 根因是 `range.insertNode` 直接塞 DOM，绕过 React/Lexical 受控 state，被 reconciliation 抹掉 → 表现为「逐字打上后又全删」。当前代码已全项目无残留 `insertNode`，改为 `execCommand('insertText')` 触发 `beforeinput`，理论正确。此方向无需回退。

### 2.3 read() 的「Draft.js 真实 state」—— 错误前提 ⚠️（中）

`engine-utils.js`、`repost-engine.js`、`nurture-engine.js` 三处 `read()` 均优先读：
```js
var leaves = editor.querySelectorAll('[data-text="true"]');
```
但 `[data-text="true"]` 是 **Draft.js** 专用选择器；X compose 实际是 **Lexical**（代码内 `scrubEditorMentions` 注释、`_nr_findCommentBox` 均自述 Lexical / `public-DraftEditor-content` 为旧残留）。Lexical 不渲染 `data-text="true"` 叶子 → 该分支**永远返回空串**，`read()` 实际恒定落到 `innerText` 兜底。

后果：
- 声称的「用真实 state 校验杜绝假成功」**并未真正实现**（死分支）。
- 功能上暂不致命：Lexical 下 `innerText` 本身就是真实态，读时不至于错。
- 但 manifest 4.6.9 描述「用 [data-text=true] 叶子做真实 state 校验」是**误导性声明**，文档与注释需更正。

### 2.4 typeTextHumanLike 多余合成 input 事件 ⚠️（中）

`engine-utils.js typeTextHumanLike` 每段循环：
```js
inserted = document.execCommand('insertText', false, seg); // 成功即已原生触发 beforeinput+input，Lexical 已更新
if (!inserted) { dispatch beforeinput }                     // 仅在失败时补 beforeinput
dispatch input                                             // ← 无条件又补一次合成 input
```
`execCommand('insertText')` 成功时已触发真实 `beforeinput`+`input`，此处再无条件派发一次合成 `input`（带 `data: seg`）属多余。多数情况下 Lexical 的 input handler 对 `insertText` 输入类型不重复处理（无害），但存在干扰受控状态同步的风险，需实测；若怀疑重复，应改为「非 inserted 才补发 input」。

### 2.5 looksOk 宽松兜底 —— 截断误判 ⚠️（中）

`insertEditorText` / `_nr_insertCommentText` / `typeTextHumanLike` 的 `looksOk`：
```js
if (got === want) return true;
var n = Math.min(8, want.length);
return n > 0 && got.indexOf(want.slice(0, n)) >= 0; // 只比对前 8 字符
```
若输入中途丢尾段（只剩前几个字符），`looksOk` 因「前 8 字符命中」判 true → 直接发布**截断正文**。这与之前「复制多文字导致发送失败」的修复意图相悖（那次摘要声称改「严格 === 优先，indexOf 兜底」，但兜底阈值过宽仍是漏洞）。建议：正文写入后一律 `got === want` 严格校验，仅当严格失败且确属「引用原文被平台截断」类例外时才放宽（当前无此场景）。

### 2.6 content_follow_v1522.js 独立旧副本 ⚠️（低/待确认）

`follow/content_follow_v1522.js:3285 __nr_insertCommentText` 是独立复制的旧版：
- 未接 `EngineUtils.typeTextHumanLike`（无人拟化键盘层）。
- `read()` 仍仅 `innerText`（未改），且无 `[data-text="true"]` 分支。
若关注流程的评论功能仍活跃，它与 nurture/repost 的输入策略不一致，同样可能踩 Lexical 受控 state 问题。是否同样修复取决于该流程是否还在用（见 §6 待确认）。

### 2.7 发布确认 / 媒体 / 反垃圾 —— 完整 ✅

成功三信号、Something went wrong 重试 3 次、反垃圾冷却、媒体闸门开合、残留 compose 强关，逻辑完整无回归迹象。

## 5. 验证步骤

1. **语法**：对改动文件 `node --check`。
2. **全量测试**：`npm test`，确认不新增失败（关注基线：历史遗留失败是否仍为 0，若复现需排查是否与本次改动相关）。
3. **19:00 实测**：临时把 `startHour` 设为当前分钟 +2，重载扩展刷新 X 页，观察是否准点拉起转帖；验证后还原 19:00。
4. **发文实测**（关键）：重载扩展 → 刷新 X → 跑一次真实转帖，观察 F12 控制台与编辑器：
   - a) 是否还出现「逐字输入后又全部删掉」；
   - b) 正文是否完整（无截断）；
   - c) 发送钮是否由 disabled 变 enabled。
5. **若仍失败**：加临时探针判定哪个输入层生效（execCommand beforeinput / paste / InputEvent），据此决定是否需要换写入口（如改为「先 paste 一次性写入 + 拟人化仅做时序抖动」的稳定方案）。
