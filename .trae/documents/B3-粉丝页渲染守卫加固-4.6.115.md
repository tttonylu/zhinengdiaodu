# B3 粉丝页渲染守卫加固：修「HaagRoyce26150 一直扫不到粉丝格」

目标版本：4.6.114 → **4.6.115** ｜ 归属子 ID：**B3 点击关注**（扫描点粉）｜ 改动文件代码仅 `unified-scheduler/follow/content_follow_v1522.js`

## 1. 问题与根因（已实机验证）

**现象**：账号领 blogger @HaagRoyce26150 后一直扫不到粉丝格；手动开 `https://x.com/HaagRoyce26150/followers` 控制台查 `document.querySelectorAll('[data-testid="UserCell"]').length` = **46** → 选择器没变、页面最终会渲染，问题在插件等待窗口与自愈动作。

**根因链（代码已核实）**：

1. **渲染等待预算太短**：进粉页 settle 8s（仅首次，`sg_follow_scan_settled_<cr>` 存 sessionStorage，L5277-5281）+ 4.6.112 加的渲染守卫 5 tick × 2s = 10s（L5362-5383）。UserCell 渲染 >18s 即判白壳。
2. **白壳首愈即硬刷，抹掉渲染进度**：守卫超时 → `scanPage()` 0 cell → `handleFollowersShellStall('scan_zero_cell_shell')`（L4529-4533）→ `requestSharedSoftHeal`（L1891）→ 页面无「重试」按钮可点时发 `sg_request_heal` → background `chooseHealMode` 对 `*_shell` reason 走默认 **`reload`（bypassCache 硬刷）**（background.js L1536-1556）→ 页面从零重新渲染。
3. **重载后预算反而更短**：settle 标记跨重载存活 → 重载后只剩 10s 守卫 → 仍渲染不完 → shell#2（60s 共用愈冷却挡掉重刷，只睡 10s）→ 守卫 10s → shell#3 … → 计数到 6 → `releasePoolTask('followers_shell_timeout')`（L1909-1915）→ 号池重派 → 循环复发。

注：SCAN 步骤超时只重置计时器（L5019-5020），不杀任务——延长守卫等待**不撞** 120s 步骤超时。看门狗在见到 UserCell 时会清 shell 计数（L2935-2938），渲染成功一次即脱循环。

### 2.2 代码（content_follow_v1522.js，共 4 处）

**① FOLLOW_PACE 加两键（L28-41）**

```js
scanLoadingGuardTicks: 10,     // 渲染守卫 10×2s=20s（原硬编码 5）
scanLoadingBusyMaxTicks: 15    // aria-busy 宽限封顶 15×2s=30s
```

**② 新增 `pageLooksFollowersLoading()`（放 L1824 `pageLooksFollowersShell` 附近）**

判定「仍在加载中」：`[data-testid="primaryColumn"] [aria-busy="true"]` 或 `primaryColumn` 内 `[role="progressbar"]` 存在即 true，异常兜底 false。

**③ 渲染守卫改造（L5362-5383）**

- 硬编码 5 改为 `FOLLOW_PACE.scanLoadingGuardTicks`（10）。
- 每 tick 先查 `pageLooksFollowersLoading()`：busy=true → **不进位**守卫计数，另计 busy tick，超 `scanLoadingBusyMaxTicks` 才放行到 shell 处理（防永等）；busy=false 才进位。
- 诊断日志升级为带证据：`⏳ followers 渲染守卫 (n/10) cells=0 busy=1`，遥测 `follow.step_mismatch` 的 detail 增加 `cells`/`busy` 字段。
- cells 一出现（`pageLooksFollowersShell()=false`）即清计数放行——**快页不多等**（现有行为保留）。

**④ `handleFollowersShellStall` 首愈不刷 + 愈后补 settle（L1891-1918）**

- 软窗外：shell#1 时**跳过** `requestSharedSoftHeal`，只 `updateStats` + 诊断「shell 首愈只等不刷」+ sleep `scanWaitMs`（10s），给在途渲染一个节拍；shell#2 起才调 `requestSharedSoftHeal`。
- 软窗内分支维持「只愈不释放」，同样保留愈动作。
- `requestSharedSoftHeal` 返回 true（真派发了愈/点了重试）时，按 `localStorage.matrix_current_creator` 清掉 `sg_follow_scan_settled_<cr>` → 重载后重新吃 8s settle，恢复「8s settle + 20s 守卫」完整预算。
- 6-cap release、`sg_follow_shell_wait_n` 语义不动（防死循环兜底保留）。

## 3. 关键决策记录

- **采信记录诊断**（渲染慢于守卫窗口）：46 cells 证明选择器/页面正常；且用户上下文刚做过 CPU 优化（4.6.113/114），慢渲染与高负载环境一致。
- **首愈不硬刷**是本次核心修复（比单纯延长守卫更治本）：硬刷会抹掉已进行的渲染，是循环复发放大器；代价是真卡壳场景首次重刷推迟 ~10s，可接受。
- **20s/30s 数值依据**：手动访问同页可完整渲染 → 渲染终会完成；X 粉丝页 GraphQL 慢响应 10-20s 常见；busy 30s 封顶防永等，且不撞 120s 步骤超时（SCAN 超时仅重置计时器）。
- **不改 background `chooseHealMode`**：默认 reload 行为本身合理，只通过「首愈不刷」减少误触发频次，爆炸半径最小。
