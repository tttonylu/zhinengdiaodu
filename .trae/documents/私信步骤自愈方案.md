# 私信（及全模块）步骤检测与自愈方案

## 摘要

用户反馈：插件修改后出现"没有进入 DM 就开始发送破冰"、"行驶路径上没有检测没有自愈"的问题。根因是各模块缺少统一的**步骤前置校验**——当前页面不是预期步骤所需的页面时，仍然执行了发送/写入等动作。

## 现状分析

### 各模块自愈能力对比

| 模块 | 页面漂移检测 | 步骤状态机 | 发送前页面校验 | 自愈回退 |
|---|---|---|---|---|
| 关注 | ✅ `classifyPage`+`expectedPageFor`+`handlePageDrift` | ✅ `matrix_step`(SCAN/PROFILE) | ✅ settle 等待 | ✅ 漂移回导航 |
| **私信** | ⚠️ 部分（`ensureInboxListRootView`） | ✅ `dan_auto_step`(1/2/2_waiting/4) | **❌ 缺失** | ⚠️ 有 40s 健康超时回收，但非步骤级 |
| 转帖 | ❌ 无 | ⚠️ pending 状态 | ✅ compose modal 等待 | ⚠️ 关窗跳过 |
| 养号 | ⚠️ 偏离首页拉回 | ❌ 无 | N/A | ⚠️ soft_reload |

### 私信流程的具体断裂点

私信的 `dan_auto_step` 状态机：
- `step=1`：导航到目标用户资料页 → 点 DM 按钮 → 进入 DM 会话
- `step=2/2_waiting`：在 DM 会话中执行发送（`sendOneOrDump`）
- `step=4`：发送完成，离开会话回列表

**断裂点**：`sendOneOrDump()`（L10865）进入后，一路做 OPS 校验、轮次判定、破冰检测、话术选取……**但从未校验"当前页面是否真的是一个 DM 会话页"**。如果 `step` 被设为 `2` 但页面实际不在 DM（比如卡在资料页、粉丝列表、首页），代码仍会尝试找 composer、写文本、点发送——结果就是"没进 DM 就开始发送"。

已有的 `isDmConversationView()`（L4586）和 `isDmConversationPage()`（L4394）只在外层健康检测和 `ensureInboxListRootView` 中使用，**没有在 `sendOneOrDump` 入口处做前置守卫**。

### 关注模块的对比（为什么关注没问题）

关注有完整的漂移检测链：
1. `classifyPage()` → 当前在什么页面
2. `expectedPageFor()` → 这个步骤应该在什么页面
3. `handlePageDrift()` → 不匹配就自愈导航回去

私信缺少等价的**步骤-页面期望矩阵**和**不匹配时自愈回退**。

## 提议改动

### 1. 私信：`sendOneOrDump` 入口加步骤前置校验（核心修复）

**文件**：`chat/content_chat.js`
**位置**：`sendOneOrDump` 函数最顶部（约 L10865，`dan_dm_inflight` 锁之后、`isFleetHandle` 之前）

**逻辑**：
```
进入 sendOneOrDump 后：
1. 校验 dan_auto_step === '2'
2. 校验当前页面是否在 DM 会话（isDmConversationView() || isDmConversationPage()）
3. 如果不在 DM 会话：
   a. 清除 dan_auto_step（回退到无 step 状态，让主循环重新导航）
   b. 上报遥测 chat.step_mismatch（step=2, page=<当前URL>, target=<handle>）
   c. Toast 提示"步骤不匹配：发送需要 DM 会话页"
   d. return（主循环下一 tick 会从 step=undefined 重新走导航流程）
4. 校验 composer 存在（hasSendableDmComposer()），不存在则同上回退
```

**防回环**：用 sessionStorage `dan_step_mismatch_count` 计数，同一 target 连续 3 次不匹配则标记 `deferred`（`iceQueueMark` + `finishTargetVisit`），避免死循环。

### 2. 私信：step=1→2 过渡时加"进入 DM 确认"（防 step 跳级）

**文件**：`chat/content_chat.js`
**位置**：主循环 `currentStep === '1'` 分支（约 L9684 附近，step1 处理逻辑的出口处）

**逻辑**：
当前 step=1 的逻辑是：导航到资料页 → 点 DM 按钮 → 设 `dan_auto_step='2'`。
问题是设 step=2 的时机可能太早（页面还在跳转中）。

**修复**：在 `sessionStorage.setItem('dan_auto_step', '2')` 之前，增加一个过渡标记 `dan_auto_step='1_entering_dm'`，只有当下一 tick 检测到 `isDmConversationView()` 时才升为 `'2'`。

### 3. 私信：主循环顶部加步骤-页面期望矩阵

**文件**：`chat/content_chat.js`
**位置**：主循环 `currentStep` 读取之后（约 L9684）

**逻辑**：
```js
var expectedPage = {
  '1': 'profile_or_followers',  // step1 应在资料页或粉丝列表
  '2': 'dm_conversation',       // step2 应在 DM 会话
  '2_waiting': 'dm_conversation',
  '4': 'any'                    // step4 离开中，不限制
};
if (expectedPage[currentStep] === 'dm_conversation' && !isDmConversationView()) {
  // 步骤说在 DM 中，但实际不在 → 回退
  sessionStorage.removeItem('dan_auto_step');
  sessionStorage.setItem('dan_step_mismatch_count', String(+1));
  // 3 次则 deferred
}
```

### 4. 转帖：compose 页面校验前置

**文件**：`repost/repost-engine.js`
**位置**：UI 路径发帖函数（约 L1100）

**逻辑**：在尝试打开 compose modal 之前，校验当前页面是否支持 compose（`/compose/post` URL 或首页有 compose 入口）。不在则先导航。已有部分等待逻辑但缺少页面级校验。

### 5. 遥测：步骤不匹配事件

新增遥测事件 `chat.step_mismatch`，上报：
- `step`：预期步骤
- `page`：当前 URL path
- `target`：目标 handle
- `mismatch_count`：连续不匹配次数

供 OPS 后台观测这类故障的频率和分布。

## 不改动的部分

- 关注模块的漂移检测链已完善，不动。
- 养号模块不涉及"进入特定页面才能操作"的步骤（只是在首页刷），不需要步骤矩阵。
- `dan_auto_step` 状态机整体结构不动（step 1/2/2_waiting/4 的语义已验证），只加前置守卫。
- 软风控、OPS 校验、话术选取等业务逻辑不动。

## 假设与决策

1. **不引入新的步骤状态**：`1_entering_dm` 是现有 `1` 和 `2` 之间的过渡标记，不是新状态，主循环已有的 step 判定（`step === '1'` / `step === '2'`）不受影响——`1_entering_dm` 不匹配任何现有分支，会走 `else`/default 分支等待。
2. **防回环靠计数**：同一 target 连续 3 次不匹配才 deferred，避免慢网下一次误判就放弃。
3. **只修私信**：用户明确提到私信的破冰问题。转帖和养号的步骤校验放后续。
4. **版本号**：4.6.109 → 4.6.110
5. **宪法对齐**：步骤状态是"实时运行态"，按真相源声明第 2 条本地持有，不涉及 OPS 对账。
