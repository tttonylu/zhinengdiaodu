# 智能调度中心 v3.0 需求规格

> 版本：v3.0.0 · 立项基线 · 2026-07-26
> 主体：`unified-scheduler/`（Chrome MV3 扩展）+ `x-pool-service` / `x-ops-console`（双后端）
> 作者：工作室老板视角立项，围绕三大主线

---

## 1. 项目定位

基于 Chrome MV3 扩展 + 双后端（号池服务 / 运营控制台）的 **X/Twitter 矩阵号自动化运营平台**，按 **关注 → 养号 → 私信** 三段式风险梯度分阶段商业化，多 worker 跨机运行，面向日本市场（话术/评论模板日文，引导至站外 LINE/落地页）。

三个原语：
- **号池**：x-pool-service 维护目标博主/粉丝任务队列，worker 主动 `pool_pop` 领号，完成后 `pool_done` / `pool_fail`。
- **运营后台**：x-ops-console 维护推广链接池、话术池（已含 10 套默认）、DM 战报、账号注册库，v3.0 起增加全量审计表、worker 注册表、阈值/模板后台可改。
- **本地扩展**：unified-scheduler 是注入到 x.com 的 Content Script + Service Worker，自动跑关注/养号/私信并在本地双 storage 持久化状态。

## 2. 现状诊断（起跳基准）

**起跳基准（立项决策写入）：**
- 部署规模：**25 个实例 × 25 个账号**
- 当前产出：**每日进粉 6-10**（手动模式已能稳定控号进粉）
- 痛点：扩到 50 + 规模就乱；封号每周 5-15%；只有总数看不到单号损益；改阈值要动代码

**6 大痛点归因（围绕三大主线）：**

| 痛点 | 归因主线 | 真相 |
|---|---|---|
| 封号太多 | 一·自动化稳定性 | 每周 5-15% 死亡但不知是谁/哪台机/哪套话术在拉爆，只能整批重训 |
| 转化/导流差 | 一·自动化稳定性 | 只有总数，没有"关注→DM→回复→LINE 跳转→成交"漏斗，永远在猜 |
| 规模跱不上 | 二·规模化 | 每周补号成稳定成本；没有 worker 注册表/任务锁，扩到 100 就乱 |
| 可控性不够 | 三·模块化 | 阈值/话术全埋在 `config.js` + `chrome.storage.matrix_config_overrides`，老板改不了策略 |
| 看不到全局 | 二·规模化 | ui_console 只能在 x.com 页面上看浮动面板，没有集中 worker 看板 |
| 代码太乱难维护 | 三·模块化 | 三套仓（DAN/号池/test-env）+ 两份后端副本 + unified-scheduler 未入 git |

**核心论断：** 当前不是"工具不够"，是**没有单号级损益表**——只要补上数据底座，6 大痛点归因自然清晰。三大主线一起抓，但 v3.0 必先建底座（M0）。

## 3. 三大主线（v3.0 立项驱动核心）

### 主线一：自动化稳定性（让自动化比手动更稳）
> 目标：无缝跑 24h 不需人工介入擦屁股，且封号率不高于手动模式

- 包含调度 v5 现有自动化能力的**保真保留**（无大改、不重写调度核心）
- 补**自愈**：卡死自动重启、网络抖动自动重试、跨页 prev 快照已实现需保留
- 补**消极反馈识别**（C6）：私信被拉黑/拒回/被举报 → 自动拉冷 + 写 audit
- 补**全量审计表**（黑盒记录仪）：每个敏感动作入库可回放，封号能定位根因

### 主线二：规模化管理（从 25 扩到 100+ 不增人工）
> 目标：扩机/扩 worker 不需要新增操作员

- **worker 注册表 + 心跳续约锁**：x-pool-service 认 worker，避免重复领号 / 死 worker 仍持任务
- **worker 状态看板**：ops-console 集中显示所有 worker 当前引擎、Day、近 N 日动作量、存活灯
- **单号损益表**：每行一账号，含年龄/Day/24h&7d 动作量/IP 段尾/话术 ID/死亡快照/漏斗指标

### 主线三：模块化方便改（老板在后台改策略不动代码）
> 目标：阈值/话术/评论模板热改，调策略无需发版

- **三仓合并 monorepo**：把 x-pool-service + x-ops-console + unified-scheduler 整入根仓 `D:\下载\智能调度`，删除 test-env / 号池 副本
- **配置层抽离硬编码**：`background.js` 内 `POOL_SERVER/OPS_SERVER/AbortSignal.timeout(5000)` 等上移到 config
- **阈值上后台**：MatrixConfig 中阶梯限额/间隔/活跃时段/预算等通过 ops-console 写 `matrix_config_overrides`
- **评论模板上后台**：B6 养号评论模板从 `nurture-comments.js` 硬编码上移到 `/api/nurture/comments`，插件按 API 拉取 + 本地兜底
- 话术池继续保留 30min 同步机制

## 7. 验收标准（"可扩规模"门槛 — v3.0 三准则全达才放扩）

| # | 准则 | 验收信号 |
|---|---|---|
| G1 | 不用人工介入能跑 24h | 连续 72h ×3 次试验，无人工介入且无明显卡死/页面漂移不归；封号率不高于手动模式 |
| G2 | 后台看到所有 worker 状态 | ops-console 一屏显示全部 worker（引擎/Day/动作量/存活/话术 ID）；死亡灯自动变红 |
| G3 | 后台改阈值不动代码 | ops-console 修改任意阈值 ≤30s 反映到全部 worker；改评论模板无需发版 |

**辅证（非门槛但需可见）：**
- 每账号 24h/7d 损益行可查
- 拉黑/拒回/被举报 → 自动拉冷写入 audit 可回放
- 领号重复事件计数为 0（任务锁生效）

## 9. 关键风险与对待

| 风险 | 描述 | 对策 |
|---|---|---|
| 工程先于业务 | 重构完业务更差 | 严格按 M0 数据底座先于 M2 工程化 |
| IP / 设备指纹未隔离 | 25 同机多 profile 拓扑扎堆被封 | v3.0 暂不解决，红线单号损益表暴露后下一轮投资代理池 |
| 话术已被平台识别 | 日文 icebreaker 模板雷同 | C6 消极反馈识别后回填死亡快照对比 |
| 号源质量差 | 号池领到死号率高 | 任务锁 + `matrix_dead_handles` 缓存（已实现）+ 死号占比入审计 |
| 后端表扩张影响生产 | audit_logs 写入高峰可能压垮 ops | 异步写 + 批量上报 + 写入失败本地入队 |
