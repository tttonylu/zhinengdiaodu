## 🔴 高优先级问题

### 问题 1：round≥3 完结判定与 kickCount 不同步

**状态**：✅ 已修复（2026-10-02）  
**涉及板块**：C1（目标库）↔ C2（分类）↔ C5（发送闸门）  
**契约表**：C1↔C2「目标库 ↔ 开人」  
**修复**：`chat/chat-gates.js` 的 `isChatFullyClosed` 补充 `entry.done` 和 `round≥3` 判定，对齐 C1/C2 语义  

**现象**：
- C1 `setUserRound`：`round≥3 → done=true`（target-db.js:188）
- C5 `isChatFullyClosed`：完结条件 = `chatClosedAt || finalKickSentAt || rejectSentAt || blockedAt || kickCount≥2`（chat-gates.js:130-134），**不看 `done` 也不看 `round≥3`**
- C5 `canSendKickNow`：只要 `!isChatFullyClosed && kickCount<2` 就认为可以发催加（chat-gates.js:116-127）
- C2 `classifyFanRosterAction`：`eff >= 3 → skipped`（content_chat.js:1361），直接判完结

**矛盾场景**：
旧数据或 OPS 同步导致某目标 `round=3, done=true, kickCount=1`（只发了盾牌，没发催加）。此时：
- C5 `canSendKickNow` 返回 **true**（认为还能发催加）
- C2 `classifyFanRosterAction` 返回 **skipped**（认为已完结，不开人）
- **结果**：该目标永远拿不到催加，但 round 已到顶，队列永不 promote

**手册依据**：
- 手册 C1：「完结：round≥3 或 reject/blocked/done」
- 手册 C5：「盾牌+催加共 2 步；不按小时等」
- 手册附录鸟瞰：「0 破冰 → 1 查回/AD或婉拒 → 2 盾牌或催加 → 3 完结」
- **round=3 语义上是完结**，但 C5 的 `isChatFullyClosed` 未对齐此语义

**建议**：在 `isChatFullyClosed` 中补充 `entry.done || (entry.round || 0) >= 3` 的判断，或在 `getKickCount` 中对 round≥3 且 done 的旧数据做更激进的兼容。

### 问题 2：chat-strategy SCRM 判定 fail-open，coTick 启动闸 fail-closed

**状态**：✅ 已修复（2026-10-02）  
**涉及板块**：A5（私信策略闸）↔ A2（主循环）  
**契约表**：A5↔H3/J「SCRM 闸」  
**修复**：`scheduler/chat-strategy.js` 的 `scrmAllowsChat` 由 fail-open 改为 fail-closed，与 coTick 启动闸一致

**现象**：
- chat-strategy.js `scrmAllowsChat()`：如果 `getScrmGateSync` 未定义或抛异常，返回 `true`（默认放行，fail-open）（chat-strategy.js:15-23）
- scheduler-core.js coTick 启动闸：如果 `getScrmGateSync()` 返回假值（缓存未就绪），`canGo=false`（fail-closed）（scheduler-core.js:4184-4188）

**影响**：
- SCRM 缓存未就绪时，`resolveChatPolicy` 可能返回 `allowChat: true`，导致策略层计算偏差（例如错误地认为 follow 应该让台、错误地进入软窗 chat 相位逻辑）
- 好在最终启动前的 SCRM 闸（coTick 第 4182 行）是 fail-closed 的，**不会真的放行私信**
- 但会导致：priority 顺序错乱、`softRiskChatBlockedFallback` 被误触发（相位被错误推进）等副作用

**建议**：chat-strategy 的 `scrmAllowsChat()` 应改为 fail-closed（无缓存默认不放行），与 coTick 启动闸保持一致。

### 问题 3：17 点定格与 job 私信时段（≥19:00）的关系不明确

**涉及板块**：A1（阶段与时段）

**现象**：
- 手册 A1：「17 点定格：禁止主动破冰新粉；对方已来信/未读收养仍可处理」
- 手册 A1：「私信时段：dating 08:00–18:00；job 10:00–≥19:00」
- 代码 `TimeUtil.chatFreezeMinutes()` 固定返回 `17 * 60`（17:00），不区分 dating/job（time-util.js:189-192）
- 代码 `chatHours.end` 是可配置的（job 可能到 19:00 或更晚），但定格点独立于 chatHours

**潜在矛盾**：
- job 模式下，17:00–19:00 仍在私信时段内，但 17 点定格禁止破冰新粉
- 这意味着 job 模式每天最后 2 小时私信时段只能清债、不能破冰新粉
- 手册未明确说明这是有意设计还是遗漏

**建议**：在手册 A1 中明确说明 17 点定格是否区分 dating/job；如果 job 模式下定格时间应延后，代码需要支持可配置的定格点。

## 🟡 中优先级问题

### 问题 4：`startChat` 旁路入口闸门不完整

**涉及板块**：A2（主循环启停）

**现象**：
- `startChat` 是手动/恢复入口（scheduler-core.js:870-927），绕过了 coTick 的完整启动链
- 它只检查了：日龄闸（Day≥3）、SCRM 闸
- 它**不检查**：私信时段、小时预算、日帽、冷却、17 点定格、关注轮让路

**对比**：coTick 的 chat 启动路径（scheduler-core.js:4046-4199）有完整的多级闸门：时段 → 日龄 → 策略 → 日帽 → 关注让路 → 软窗 → 冷却 → 预算 → SCRM

**风险**：
- 手动「只私信」模式可能在非私信时段启动
- 可能突破日帽/小时帽
- 可能与关注轮抢导航

**说明**：这是手动入口，产品可能设计为「用户主动操作则放行」。但如果手动模式也应遵守基本业务规则，则需要补闸。

**建议**：明确手动模式的边界。如果手动模式也要遵守时段/日帽/日龄，需要在 `startChat` 中补充检查。

### 问题 5：软窗 chat 被 SCRM 挡时整窗相位被推进（短暂离线浪费软窗）

**涉及板块**：A4（软风控优先级）↔ A5（私信策略闸）  
**契约表**：A4↔C

**现象**：
- 软窗内 chat 被 SCRM 挡住（客服离线）时，`softRiskChatBlockedFallback` 会被调用（scheduler-core.js:4223-4238）
- 该函数调用 `markSoftRiskChatPass1Done`，推进相位：chat1 → nurture →（近窗尾）chat2 → 清窗
- 结果：如果 SCRM 只是短暂离线（比如 2-3 分钟），整个软窗（15-17 分钟）的 chat 相位可能被完全烧掉

**手册依据**：
- 手册 A4：「chat 被 SCRM/预算挡 → softRiskChatBlockedFallback」
- 但未区分「短暂离线」和「全天离线」

**潜在优化**：对于 `scrm_pending`（缓存未就绪）已经处理了（临时养号不推进相位，scheduler-core.js:4204-4217）；但对于 `scrm`（明确不放行），如果是短暂波动，可以考虑设置一个宽限期，不立刻推进相位。

**说明**：这可能是有意设计（SCRM 不放行就不该发私信，哪怕浪费软窗），但值得确认产品意图。

### 问题 6：B4 `canEnterSoftRiskChat` 双重 fallback 缺少时段检查

**涉及板块**：B4（软风控填窗）

**现象**：
- `soft-risk.js` 的 `canEnterSoftRiskChat` 有三级回退：
  1. 优先检查 `sg.softRiskUntil` 是否活跃（防止重复进窗）
  2. 然后检查 `SgSoftFillMode.resolve()`（正式路径，含时段检查）
  3. 都不可用时 fallback 到：`StageDetector.isChatTime()` + `currentDayCount() >= 3`（soft-risk.js:49-53）
- 但**如果 `SgSoftFillMode` 和 `StageDetector` 都未加载**，第 53 行直接返回 `currentDayCount() >= 3`，**不检查私信时段**

**风险**：极端情况下（软风控模块先于阶段检测模块加载，且 SgSoftFillMode 未注入），非私信时段也可能进入 chat_fill 模式。概率极低但逻辑上有缺口。

**建议**：在 fallback 路径中也补充时段检查，或确保注入顺序保证 SgSoftFillMode 始终先于 soft-risk 加载。

## 🟢 低优先级问题（冗余 / 代码质量 / 维护风险）

### 问题 7：`classifyFanRosterAction` 中完结条件重复检查

**涉及板块**：C2

**位置**：content_chat.js:1361

```js
if (isChatFullyClosed(entry) || entry.rejectSentAt || entry.blockedAt || entry.chatClosedAt || entry.done || eff >= 3 || kc >= maxK)
```

`isChatFullyClosed` 内部已经检查了 `rejectSentAt / blockedAt / chatClosedAt / kickCount>=2`，外层又重复检查了一遍。虽然不影响正确性，但维护时容易漏改一处。

---

### 问题 8：`applySoftRiskPriority` 中 nurtureOnly 双重处理

**涉及板块**：A4

**位置**：scheduler-core.js:2127-2130 和 2169-2176

- 第 2127 行：`nurtureOnly && softRiskActive → coerceSoftRiskNoChat`（压成只养号）
- 第 2169 行：又一次判断 `nurtureOnly → return ['nurture']`

两处逻辑方向一致但有重叠，增加维护成本。

---

### 问题 9：coTick 中 priority 被 applySoftRiskPriority 计算两次

**涉及板块**：A2/A4

**位置**：
- 第 3383 行：tick 开头 `priority = applySoftRiskPriority(priority, sgTick, nowTick)`
- 第 4000 行：launch 前 `priority = applySoftRiskPriority(priority, sg, now)`

中间 sg 可能变化（例如 `coerceSoftRiskNoChat` 被调用），所以需要重算。但两次计算之间的状态变化追踪困难，容易出现「开头算的和结尾算的不一样」的隐性 bug。

---

### 问题 10：SoftFillMode 有两套几乎相同的实现

**涉及板块**：A4/B4

**两套实现**：
1. `shared/soft-fill-mode.js` → `SgSoftFillMode.resolve()`（官方版本）
2. `scheduler-core.js` → `resolveSoftFillModeCo()` 内的 fallback 实现（scheduler-core.js:2099-2111）

逻辑几乎完全一致：模块开关 → sticky nurture → 日龄 → 时段 → chat_fill。

**风险**：两套实现容易在未来迭代时出现不一致（比如一处加了新条件，另一处忘了加）。

**建议**：fallback 路径尽量简短，或直接删除 fallback（假设 SgSoftFillMode 总是先加载）。

## 审查方法说明

本审查采用「手册不变量 → 代码实现 → 跨模块契约」三层对照法：

1. **单板块验证**：每个子 ID（A1/A2/A4/B4/C1/C2/C3/C5/C9）对照手册对应章节，逐条验证不变量是否在代码中体现
2. **跨模块契约验证**：对照手册 §X 契约表，检查模块间接口字段和语义是否一致
3. **边界场景推演**：考虑极端情况（模块未加载、缓存未就绪、旧数据迁移、短暂离线）下的行为正确性

未覆盖的板块：D 养号引擎细节、E 转帖引擎细节、B3 关注点击细节、F 配置同步全量、G 面板、H OPS 后台、I 号池、J SCRM、K 自愈。这些板块的逻辑复杂度相对较低，或依赖外部服务，暂未纳入本次核心逻辑审查。
