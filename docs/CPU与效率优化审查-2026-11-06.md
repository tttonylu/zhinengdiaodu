## 0. 结论摘要

当前版本已经做过十余轮 CPU 治理，定时器门控、观察器收窄、面板降频、空闲 park、舰队租约都已落地，继续在旧热点上做微调收益有限。本轮审计真正值得做的，是下面八件事，按收益排序：

0. **后台标签拿不到配置（4.6.160 修复已丢失）**：`config-sync.js` 的 `fetchRemote` 首行是无条件 `if (document.hidden) return;`，BitBrowser 后台页永远拉不到 `stage_tick_interval_ms=30000`，coTick 一直按 10 秒跑。`config-sync-hidden-fetch.test.js` 的 4 条用例一直失败，说明这是一次未被发现的回归。这一条对 CPU 的影响可能大于后面所有项。
1. **页面瘦身（K3 四针）开关是断的**：OPS 有 `page_slim_mode` 开关，但插件里没有任何代码把远程值写成 `sg_page_slim`，MAIN 层限频、CSS 禁动效、X 遥测 DNR 拦截、评论逐键跳过四针全部不生效。这是现成的、收益最大的 X 页面侧降 CPU 杠杆，修复约 15 行。
2. **配置同步每分钟无条件重写**：50 个实例 × 每分钟 1 次配置拉取，且不管配置有没有变，每个页面都要重新解析并同步写 5 个 localStorage 键。加配置版本/ETag 短路后，大部分轮询可以变成零解析、零写入。
3. **14 处整页 `innerText` 仍在**：其中 `content_chat.js:10523` 每个私信目标 step1 都读一次整页，X 大 DOM 下每次强制同步排版 50–300ms。4.6.131 计划过但未执行。
4. **shadow DOM 深扫仍是 `querySelectorAll('*')`**：私信每个步骤会调用十余次，每次把整棵元素树枚举一遍。改 TreeWalker 即可，语义不变。
5. **OPS 监控页每 30 秒做一次全量日志聚合**：`hourlyTrend` 对每行调 JS 函数 `zhdate()`，24 小时约百万行，且 better-sqlite3 同步执行会卡住整个 Node 事件循环。改成字符串截取 + 60 秒缓存，收益立竿见影。
6. **错误中心一次页面加载跑 11 次全区间 COUNT**：`boardBreakdown` 对每个板块各扫一遍 `meta_json LIKE`，可合并成一次 `GROUP BY category`。
7. **DOM 全量计数每 60 秒一次**：调度侧明明可以直接复用 chat 侧已写好的 `dan_dom_count`，现在仍在 `getElementsByTagName('*')` 重数。

结构性的大改（54 个脚本全量注入、约 22 个定时器合并成中心时钟、按页面类型条件注入）不建议现在做。先把上面这些定点收益拿到，再用遥测决定是否值得动架构。

## 1. 项目理解

这是一套「多开 Chrome 档位 + 单账号单实例」的 X 运营系统。每个 BitBrowser 实例里跑同一个 MV3 扩展，扩展在 `x.com` 页面注入 54 个内容脚本，由 `scheduler-core.js` 的 `coTick` 做唯一调度大脑，按 S0–S4 阶段在关注、私信、养号、转帖四个引擎之间轮转；配置由 OPS（`:15680`）下发，博主任务由号池（`:15678`）分发。

运行模型决定了 CPU 的两个基本盘：

- **X 页面自身**是主线程大户。React 重渲染、虚拟列表、图片/视频解码、页面自己的秒级轮询，都发生在 MAIN world，插件只能间接影响（禁媒体、DNR、页面瘦身、减少滚动和 DOM 变更）。
- **插件侧**的成本主要不是单次计算，而是「50 个实例 × 每个实例的常驻轮询」。所以任何「每标签每分钟一次」的东西，在舰队规模下都会被放大 50 倍。

当前文档的硬边界仍然有效：不改业务判定语义、不主动拆巨石文件、改阈值键要 OPS + config-sync + 引擎三处同改、行为变更要 bump manifest 并记 §13。本报告的建议都按这个约束写。

## 4. 页面侧（浏览器）可优化项

### P0-0 后台标签配置拉取回归，coTick 一直按 10 秒跑

**证据：**

`shared/config-sync.js:721` 的 `fetchRemote()` 第一行就是：

```js
if (document.hidden) return;
```

而 4.6.160 的 §13 记录明确写过「hidden 首次仍拉、之后 5 分钟内跳过、满 5 分钟补拉、切回前台立即拉」，仓库里也确实有对应的 `test/config-sync-hidden-fetch.test.js`，4 条用例分别覆盖这四个行为。当前代码这 4 条全部失败（`expected 1, actual 0`），说明修复在后续改动中丢失了，而测试没有进入发布门控。

**影响：**

BitBrowser 多开的后台页 `document.hidden === true`，配置同步直接 return，OPS 下发的 `stage_tick_interval_ms`、`stage_watchdog_ms`、模块开关、阈值全部到不了后台页。结果就是后台页的 `coTick` 一直用插件内置默认 10 秒，而不是 OPS 配置的 30 秒——50 个实例的调度心跳次数是应有值的 3 倍。这一条的 CPU 影响很可能大于本报告其余所有项。

**建议：**

恢复 4.6.160 行为：`fetchRemote` 在 hidden 时用 5 分钟窗口（首次仍拉、窗口内跳过、满窗补拉），并在 `startSync` 注册 `visibilitychange`，切回前台立即拉。改动约 15 行，已有 4 条单测可直接验收。

**风险：**

低。hidden 状态下最坏 5 分钟才拿到新配置；可见页不受影响。这个延迟换回的是后台页 tick 从 10 秒降到 30 秒。

### P0-1 页面瘦身开关断链，四针全部未生效

**证据：**

- OPS 配置页有 `page_slim_mode`（off/gray/on）和灰度账号勾选，`config.njk:342-344`。
- 但 `shared/config-sync.js` 的 `storageSet` 只写了 `sg_media_load_mode`，没有 `sg_page_slim`（`config-sync.js:584-588`）。
- 全仓库搜索 `sg_page_slim`，只有读取方：`media-block-sync.js`、`media-block-main.js`、`background.js`、`content_follow_v1522.js`，**没有任何写入方**。
- 更隐蔽的是：MAIN world 和关注引擎读的是 **localStorage** 的 `sg_page_slim`，而配置同步即使补写，按现有设计写的是 **chrome.storage.local**；两边不互通。

**影响：**

4.6.147 设计的四针全部处于关闭状态：

1. `html.sg-page-slim` CSS 禁动效；
2. MAIN world 把 X 的 `setInterval` 钳到 ≥2000ms、`requestAnimationFrame` 合到约 10fps；
3. DNR 拦截 X 自家遥测（jot / ads-api / analytics）；
4. 评论输入跳过逐键模拟。

这四针针对的正是「X 页面本身占大头」的那部分 CPU，是现成方案里性价比最高的一组。现在只有手工在控制台写 `localStorage.sg_page_slim_force='1'` 才能局部验证。

**建议：**

在 `config-sync.js` 的 `applyPayload` 里恢复 K3 门控：读 `page_slim_mode` 与 `page_slim_handles`，按当前 handle 匹配 gray 清单，得到 `on/off`；同时写 `chrome.storage.local.sg_page_slim` 和 `localStorage.sg_page_slim`，并派发 `sg-page-slim-changed` 事件。`sg_page_slim_force` 的本地强制优先级保留。

**风险与验证：**

风险主要是瘦身可能改变业务时序（评论输入、页面轮询）。建议先 gray 10 个号跑一个完整工作日，验收看三件事：控制台 `window.__sgPageSlimOn()` 为 true、`document.documentElement.classList.contains('sg-page-slim')` 为 true、单实例任务管理器 CPU 相比未开号下降；同时业务指标（关注数、私信发送数、评论成功率）不下降。

改动归属：F1 + K3，版本例 4.6.194。

### P0-2 配置同步加版本短路，避免每分钟无条件重写

**证据：**

`background.js:1078` 的 `fetch_remote_config` 直接 `opsFetch('/api/config/all?bot_id=...')`，没有缓存；每个页面的 `config-sync.js` 每 60 秒拉一次，拿到后不管内容是否变化，都会 `JSON.stringify` 并重写 `sg_stage_policy`、`sg_module_switches`、`sg_config_thresholds`、`sg_config_intervals`、`sg_nurture_remote_cfg` 五个 localStorage 键（`config-sync.js:593-598`），部分路径还会写 chrome.storage。

需要先说明一个容易误判的点：BitBrowser 多开是**独立浏览器实例**，各壳不共享 SW 和 storage。所以「SW 缓存」只能合并同一壳内的多标签请求，跨 50 个壳并不会减少 OPS 请求。真正的收益有两块：

- **页面侧**：配置没变时不做 JSON 解析和写盘。50 个页面 × 每分钟 5 次同步 localStorage 写入，是稳定存在的常数开销，且 `localStorage.setItem` 是同步 API，会占主线程。
- **OPS 侧**：把 `/api/config/all` 的组装结果按 `bot_id` 做 30–60 秒内存缓存，或在响应里带 `ETag`，插件用 `If-None-Match` 拿 304。重复轮询不再做账号 override 合并和多次 DB 读取。

**建议：**

OPS 给配置响应加版本号或 ETag（配置保存时自增）；插件保存上次版本，版本一致就直接 return，不解析、不写盘。同时 SW 对同一 `bot_id` 的并发请求做单飞，避免一个壳里多个标签同时触发时重复拉取。这一步不改变任何阈值语义。

**收益：**

配置未变时页面侧从「每分钟 5 次写 + 若干次 JSON 解析」降为「一次比较」；OPS 侧重复轮询不再触发 DB 组装。不是 50 倍请求量下降，而是把每分钟的固定写放大去掉。

**风险：**

低。版本号必须覆盖所有会影响插件行为的配置来源（全局阈值、账号 override、阶段策略、模块开关），漏一个就会出现「改了不生效」。建议用 OPS 侧统一的 `config_version`，任何写配置的入口都自增。

### P0-3 剩余整页 `innerText` 定点清理

**证据（按热度排序）：**

| 位置 | 场景 | 频率 |
|---|---|---|
| `chat/content_chat.js:10523` | step1 每目标读整页判断账号阵亡 | 每个私信目标一次 |
| `chat/content_chat.js:4504` | `isEmptyDmStartShell` 判断空壳会话 | 每次进会话，调用 2 次 |
| `chat/content_chat.js:8414` | 只读会话兜底 | 每次可发三态判定未命中时 |
| `chat/content_chat.js:2424/2457/2465/2473` | 粉丝数兜底、拉黑/保护/阵亡判定 | 每轮 step1 的兜底路径 |
| `follow/content_follow_v1522.js:3766` | 冻结/限制文案兜底 | 每次 `checkLimits` 兜底 |
| `dm-pin.js:92` | PIN 门文案采样 | 每次 PIN 闸判定，单次最多调 4 次 |
| `nurture-engine.js:341/350`、`repost-engine.js:816`、`scheduler-core.js:504` | 各类页面文案判定 | 低频，但同样是整页排版 |

`innerText` 是排版感知 API，DOM 脏时读取会强制 Chrome 做一次同步布局。X 的 DOM 规模下，文档记录的单次成本是 50–300ms。这已经不是「微优化」，而是单点卡顿源。

**建议：**

逐处替换为 `textContent`；能用更窄根节点的（`primaryColumn`、会话面板、按钮容器）就不要再读 `document.body`。正则一字不改。按 4.6.131 的门控方法执行：替换前在真实页面同时取 `innerText` 与 `textContent`，对每条正则做 match 对比，结果一致才发布；不一致的保留原样并记录原因。

**风险：**

`textContent` 会包含 `<script>`/隐藏元素文本，存在误判可能。双值对比是发布强制门控，不是可选项。

### P0-4 shadow DOM 深扫改 TreeWalker

**证据：**

`chat/content_chat.js:8015` 与 `8043` 在每一层 shadowRoot 上执行 `root.querySelectorAll('*')`，只为了找带 `shadowRoot` 的宿主；`dm-pin.js:67` 同样写法。`__dmQueryAllDeep` 在私信链路有 10 个以上调用点（8113、8174、8188、8248、8267、8281、8313、8381、8457、8517），每个步骤可能反复枚举整棵树。

**建议：**

用 `document.createTreeWalker(root, NodeFilter.SHOW_ELEMENT)` 一次遍历元素节点，在遍历中检查 `node.shadowRoot` 并递归；不再构造 NodeList，也不触发选择器匹配。深度上限 6、open shadowRoot 递归、maxLen 截断全部保留。进一步可以按 URL/会话缓存 shadow 宿主列表，软导航时失效。

**收益：**

私信页每次找输入框、找按钮、采文案的成本从「全树枚举 × 多层」降到「一次线性遍历」，在 X 把 DM 面板整体放进 shadow 的当前结构下尤其明显。

### P1-1 DOM 全量计数复用缓存

**证据：**

`scheduler-core.js:456` 的 `coProbeMemoryPurge` 每 60 秒执行一次 `document.getElementsByTagName('*').length`；`content_chat.js:12582` 的内存监控每 5 分钟也数一次，并把结果写进 `sessionStorage.dan_dom_count`。

**建议：**

调度侧优先读 `dan_dom_count`，超过 10 分钟才本地重数；chat 侧保留原逻辑。这样每分钟一次的全树枚举降为零。属于 4.6.132 预案里一直没执行的一条。

### P1-2 `push_blogger` 的 10 秒主循环按路由收窄

**证据：**

`follow/push_blogger.js:505` 每 10 秒执行一次 `main()`，内部会扫 `article`、`UserCell`、`UserName` 并注入按钮；MutationObserver 在非关注运行、非隐藏时也一直挂着。

**建议：**

按路由门控：只在 `/home`、`/{handle}`、`/followers`、`/following` 这类可能出现推博主按钮的页面执行；私信页、发帖页、通知页直接跳过。空闲时把 10 秒放宽到 30 秒。关注引擎在跑时已经会断开观察器，这个逻辑保留。

**收益：**

舰队规模下，50 个标签每 10 秒少一次全文档选择器扫描，属于稳定的常数级下降。

### P1-3 低频轮询改为「版本未变不写盘」

**证据：**

推广链接 5 分钟（`promo-links.js:14`）、话术 30 分钟 × 2 池（`content_chat.js:466`）、媒体状态 60 秒（`media-block-sync.js:155`）、台账心跳 180 秒（`content_chat.js:2701`）。这些请求大多返回和上次一样的内容，但拿到后仍会 `JSON.stringify` 比较或直接写 localStorage。

**建议：**

和 P0-2 同一套思路，不追求跨实例合并（实例之间本来就不共享），而是让每个实例在「内容未变」时零写入：服务端给话术池、推广链接加版本号或 ETag；插件先比较版本，一致就直接返回。媒体状态只有几个字节，可以最后再做。推广链接的 5 分钟频率可以放宽到 15 分钟，话术 30 分钟可以放宽到 60 分钟——这些数据变更本来就是运营手动操作，不需要分钟级生效。

### P1-4 遥测批量参数按可见性调整

**证据：**

`shared/telemetry.js:10-12`：批量 40 条、30–60 秒 flush，每标签独立。50 个标签在私信高峰期可能形成持续的批量上报流。

**建议：**

隐藏标签把批量提高到 100 条、间隔放宽到 2–5 分钟；可见标签保持现状。4.6.178 刚修过 flush 闩死，调整时必须保留 20 秒看门狗和 `telemetry_flush_now` 唤醒路径，避免重新出现「心跳在、日志死」。

### P1-5 coTick 内 storage 读取做拍内快照

**证据：**

`coTick` 函数体内有约 39 处 `localStorage.getItem` / `sessionStorage.getItem`，`coLoadSg()` 每次都是 `JSON.parse(localStorage.getItem('sg_state'))`，同一拍内被反复调用。

**建议：**

在 tick 开始时取一次 `sg` 快照，沿调用链传递；本拍内所有写入走 `coSaveSg` 后更新快照。注意跨拍状态不要缓存，避免读到旧值。收益取决于 coTick 当前实际耗时，属于「顺手做」级别。

---

### P1-6 健康探测加 2 秒缓存

`isPageHealthyDom` 每拍最多 10 个 `querySelector`，未命中时还要读 `primaryColumn.innerText`。可以加 2 秒结果缓存，并把 `innerText` 换成 `textContent`。单次成本不高，但它是每拍都跑的路径。

---

### P2-1 注入面本身（暂不动）

54 个脚本、2.13 MB，在每个 x.com 页面解析并执行。这是固定成本，也是「50 开」内存和启动开销的一部分。但 X 是 SPA，软导航不会重新注入，按 URL 条件注册会破坏模块轮转，必须改成动态注入或路由懒初始化，属于架构级改动。建议等 P0/P1 的数据出来后再评估，不要现在动。

### P2-2 中心时钟（暂不动）

约 22 个 interval 合并成一个 1 秒 tick + 到期表，能减少定时器唤醒次数。但 Chrome 的定时器本身很便宜，真正贵的是回调里的工作；在 P1 的路由门控和缓存做完后，中心时钟的边际收益会更低。暂缓。

## 5. 后台服务（OPS / 号池）

### B0-1 监控统计查询：去掉逐行 JS 函数 + 加缓存

**证据：**

- `monitor.njk:7` 用 `meta refresh` 每 30 秒整页刷新。
- 刷新后 `/api/monitor/logs/stats` 调 `hourlyTrend`、`severityBreakdown`、`DISTINCT account_handle`。
- `log-repo.js` 的 `hourlyTrend` 与 `rollupEvents` 使用 `strftime('%Y-%m-%d %H:00', zhdate(created_at))`；`zhdate` 是 Node 侧注册的 JS 函数（`db/client.js:44`），SQLite 会对范围内每一行回调一次。
- `created_at` 在写入时已经被 `zhDateSql(e.time_zh)` 归一成 `YYYY-MM-DD HH:MM:SS`（`routes/api/plugin.js:1216`），所以 `zhdate()` 在这里是多余的。

**建议：**

把 `strftime(..., zhdate(created_at))` 改成 `substr(created_at, 1, 13) || ':00'`；统计结果加 60 秒进程内缓存（按 `hours + account` 分键）；把监控页刷新从 30 秒改为 60 秒。24 小时百万行级别的聚合，去掉逐行 JS 回调后通常有一个数量级的差距。

**影响：**

better-sqlite3 是同步 API，一次慢聚合会卡住整个 Node 事件循环，连带 config、log/batch、dm/check 全部排队。这不是「监控页慢一点」的问题，而是会放大成全局超时。历史已经发生过同类事故（4.6.176 的台账快照全表扫描）。

### B0-2 错误中心 11 次全区间扫描合并成 1 次

**证据：**

`routes/pages/errors.js:41` 调 `boardBreakdown`，内部对 11 个板块各执行一次 `countEvents`，每次条件都是 `meta_json LIKE '%"board":"X"%'` 加时间范围。等于同一段时间扫 11 遍。

**建议：**

入库时把 board 写进 `category`（现在 `category` 已有值），页面改成一条 `SELECT category, COUNT(*) ... GROUP BY category`；`meta_json LIKE` 只保留给临时搜索。若暂时不想改入库，也可以先用一条 SQL 把 11 个 LIKE 用 `SUM(CASE WHEN ...)` 一次算完。

### B1-1 日志明细保留期重新评估

当前明细保留 30 天（`log-retention.js`），按历史 120 万条/天估算，窗口内约 3600 万行。监控统计只查最近 24 小时，却要和 30 天的数据共享同一张表和同一套索引。若磁盘或查询延迟有压力，可把明细保留降到 14 天，趋势继续用 `log_rollups_hourly`（保留 180 天）。这会牺牲「一个月前的单条日志可检索」，需要运营确认。

### B1-2 `LOWER(account_handle)` 等值化

`log-repo.listEvents/countEvents` 用 `LOWER(account_handle) = LOWER(?)`，无法走索引。写入端已经做了 handle 归一化，读侧可以直接等值比较。属于顺手优化，优先级低于 B0-1/B0-2。

### B2-1 同步 SQLite 的长期解

如果做完 B0 系列后 OPS 仍偶发事件循环卡顿，再考虑把统计查询移到 worker thread，或启动时预计算每分钟快照供页面读取。现在不建议直接上 worker，先把查询本身变便宜。

## 6. 不建议做的事

**不要再增加诊断仪表。** 4.6.190 刚把定时器包裹关掉，就是因为每次 `setTimeout` 都抓栈在 50 开下代价明显。需要定位时临时 `localStorage.sg_cpu_profile='1'` 刷新即可，不要恢复常驻。

**不要为了「更模块化」拆巨石文件。** README 和 §13 已经明确冻结模块化；`content_chat.js` 758 KB 确实是维护负担，但现在拆它带来的回归风险远大于收益。

**不要靠放宽 45 秒回收阈值、降低业务频率来解决 CPU。** 这类改动会把「CPU 高」换成「任务卡住/漏发」，历史上已经踩过。

**不要在没有双值对比的情况下批量替换 `innerText`。** `textContent` 包含 script/隐藏文本，X 页面 JSON 里可能含有正则要匹配的词，必须逐条验证。

## 7. 建议落地路线

### 第 0 批：今天就能验证，不改代码

挑 2 个测试号，在 x.com 控制台执行 `localStorage.sg_page_slim_force='1'` 后刷新，观察任务管理器单实例 CPU 与业务是否正常。这一步能在写代码前确认「页面瘦身到底值多少」。同时确认 OPS 的 `fleet_heavy_slots` 已部署且生效（默认 8），离线壳及时关窗。

### 第 1 批：4.6.194（低风险、高确定性）

恢复后台标签配置拉取（P0-0）+ `page_slim` 接线（P0-1）+ 话术版本短路 + DOM 计数缓存。先 gray 10 个号，观察一个完整工作日（含 10–19 点私信窗）。

验收：后台标签的 `sg_config_thresholds.stage_tick_interval_ms` 为 30000；`window.__sgPageSlimOn()` 为 true；`cpu.profile_minute` 单账号小时总耗时相比前 7 天均值下降；关注/私信/评论成功率不下降。

### 第 2 批：4.6.195

配置版本短路 + OPS 侧配置缓存（P0-2）、shadow 深扫改 TreeWalker（P0-4）、`push_blogger` 路由门控（P1-2）。

验收：配置未变时页面侧 `localStorage.setItem` 调用数显著下降；OPS `/api/config/all` 的 304 比例或缓存命中率 >90%；`chat_scan_surface` 的 `surface_miss` 不上升；推博主按钮出现延迟不超过 30 秒。

### 第 3 批：4.6.196

话术/推广链接/媒体状态轮询集中到 SW（P1-3）、遥测按可见性调参（P1-4）、coTick 拍内快照（P1-5）。

### 后台批次：随 OPS 部署

`zhdate` 替换 + 统计 60 秒缓存 + 监控页 60 秒刷新（B0-1）；错误中心合并查询（B0-2）；视磁盘情况评估日志保留期（B1-1）。

### 第 4 批：只在数据支持时做

注入面裁剪、中心时钟。若前三批做完后单账号 CPU 已可接受，直接停止，不要为了架构而架构。

## 8. 度量口径

每次发布后至少看下面几组数，不要只看任务管理器截图：

| 指标 | 来源 | 用法 |
|---|---|---|
| `cpu.profile_minute` | OPS `log_events` | 按账号、按小时汇总总 ms；对比发布前 7 天均值 |
| `§coTick.*` 分段 | 控制台 `window.__sgCpuProfile()` | 需要时临时开仪表，定位 coTick 内部残余热点 |
| `system.pressure` | OPS `log_events` | L2 条数应趋近 0 |
| `scheduler.chat_zombie_reclaim` | OPS `log_events` | 应保持个位数到几十，不应随压力上升 |
| 业务产出/CPU 小时 | 关注数、`ice_sent`、转帖数 | 效率指标：同样的 CPU 时间是否产出更多 |
| 配置缓存命中率 / 304 比例 | OPS 访问日志 / 反代 | P0-2 的直接验收 |
| 日志查询耗时 | OPS 进程日志或 `EXPLAIN QUERY PLAN` | B0 系列的验收 |

CPU 仪表默认关闭。需要采数时，在刷新前执行 `localStorage.sg_cpu_profile='1'`，采完删掉或置 0，不要长期开着。

## 9. 需要拍板的决策点

1. **页面瘦身先 gray 还是直接全量？** 建议 gray 10 个号一个工作日；如果测试号 CPU 下降明显且业务无异常，再全量。
2. **配置版本短路是否覆盖所有写配置入口？** 全局阈值、账号 override、阶段策略、模块开关、话术池、推广链接都要纳入同一个版本号；漏一处就会「改了不生效」。这需要 OPS 侧配合排查所有写入点。
3. **舰队重活并发维持 8 还是下调？** 下调能进一步压 CPU，但会拉长单号完成时间；这是吞吐与 CPU 的取舍，需要运营定。
4. **监控页刷新 30 秒改 60 秒可以吗？** 如果可以，B0-1 的收益会更稳定。
5. **日志明细保留 30 天是否必须？** 如果只用于排障，14 天通常够；如果要留一个月的单条追溯，就保持 30 天并接受更大的表。

## 10. 审查边界

本报告基于静态代码与既有文档，没有连生产 OPS 拉最新遥测，也没有在真实 BitBrowser 实例上做 A/B。P0-1 的「开关断链」是代码级确定事实；CPU 收益的绝对数字需要在第 0 批实测确认。所有改法都应按项目既有约束拆成独立版本、单子 ID、带单测与 §13 记录，不要一次性混在一个版本里。
