# 回复逻辑与「不回复」条件

本文只讲判断顺序和结论，不要求读代码。对应测试副本 4.9.157。

## 4.9.157 “读完回复但先不发”不等于“已处理”

**现象：** 对方回了 3 条，后台也写了 `reply_verdict=reply_detected`，
但这个人之后再也没被打开过，列表里看起来就是“漏掉了”。

**原因：** 收口后的会话复活一次就会记 `已呈现`。旧逻辑把“判定为等待下一轮”
（例如催加还没到点）也算成“已处理”，于是同一个人被永久跳过。

**现在的规则：**

- 只有「已经发出动作」「确认没有新回复」「业务规则明确跳过」三种，才算处理完。
- 判定为“等下一轮”时，写 `reopenRetryAt`（15 秒 ~ 10 分钟，取等待时间的较小值）
  与 `reopenRetryReason`，到点重新复活，不会被当成已读。
- 重试等待期间对方**又发来新消息**（列表预览变化 / 精确未读）→ 立刻复活，不等原定时间。
- 后台看得到：`revived_reason = reopen_retry_wait`，
  扫描丢弃里新增「已读到回复、等下一轮才发（排队重试）」。

**什么时候仍然不回复（与之前一致）：**

- 已婉拒（年龄低于门槛）、已拉黑、对方威胁拉黑
- 对方关闭收件箱（6 小时后复查）
- 已终催完结，且收口后没有新入站
- 对方先私信但不在粉丝列表（守箱不补破冰，破冰只能从粉丝列表发起）
- 非文本入站（图片/贴纸/语音，当前只记录 `peer_non_text_unhandled`，不自动回）
- 夜间非工作时段
- 48 小时无扫描证据只延后，不永久拉黑
- 催加等待中（`kick_wait`，下一轮轮询才发）

## 4.9.157 破冰为什么之前一直做不完

**现象：** 拉新阶段扫完粉丝列表，队列里有人待破冰，但每次都停在
`/<handle>` 个人主页，85–105 秒后被 `chat.engine_watchdog reset_roster`
拉回收件箱；下轮又重复同一个人。

**两个技术原因（都不是业务规则）：**

1. 看门狗按“进入拉新阶段多久”判卡死（90 秒）。封口后逐个开人本来就要离开
   粉丝列表，时间必然超过 90 秒。
2. 拉新阶段把“离开粉丝列表 60 秒”当成页面走丢，直接退出拉新。

**现在的规则：**

- 只要私信引擎还在写进度（排空队列 / 等私信按钮 / 进会话），看门狗不按进入时长复位。
- 有在飞的破冰任务时（`dan_auto_step` + 当前目标），在资料页/会话页不算页面走丢。
- 真的停死（150 秒没有任何私信进度）仍然复位，保留自愈能力。

**验收：** 后台应看到同一个目标从 `doing` 推进到点私信、进会话；
不应再出现 `reset_roster` 打断破冰。

**附加保护：** 资料页没渲染完（读不到 `UserName` / `profileHeader` / 标题）时，
不能把“暂时找不到私信按钮”当成“对方没开私信”。现在最多等 6 拍，
仍读不到就记为 `profile_not_ready` 延后到下一轮，并上报 `chat.profile_not_ready`；
只有资料页真的渲染出来、确实没有私信按钮，才会进 `no_dm` 终态。

## 4.9.114 三种「查不出原因就不回复」

这一版修的不是判定规则，而是**反馈里根本看不到这个人**。

1. **心跳只剩空壳。** 探针和正式心跳同名同闸，探针先发就把正式心跳挡掉，
   后台每分钟只有一条 `{probe, phase, at}`，没有引擎状态、没有待处理台账。
   现在正式心跳先发、探针后补，每分钟都能看到完整状态。
2. **台账有、列表找不到，只给一个数字。** 现在会点名上报
   `not_seen_samples`（谁、第几轮、miss 几次、上次结论）。
   这类会话在列表上不出现，未读和对方最后发言都抓不到，只能靠点名查。
3. **没 peerId 也没显示名，被当成「会话不存在」永久关闭。**
   这种条目永远匹配不上列表，旧逻辑 12 次后收口，真人就此消失。
   现在单独标记为「身份缺失、无法匹配」，不计入「找不到会话」，也不再自动收口。
   注意：键写成 `p<peerId>` 的台账**不算**没身份，peerId 只是没写进字段，
   现在会从键里补回来；真实 `@handle` 也算可匹配。
   只有 `dn_<显示名>` 这种合成键，才是真的对不上人。

**判断标准：** 后台出现 `not_seen_unmatchable` 大于 0，说明台账里有身份缺失的条目，
必须补 peerId 或显示名，否则它会一直不进入任何判定。

## 4.9.113 后台说“没活”，可能只是数字没算

这一版修的是**反馈失真**：脉冲确实在扫，但后台永远显示“未读 0、对方最后发言 0”，
于是看起来像“没人回”，实际只是这两个数字根本没被统计。

- 现场证据（2026-11-13 13:58，标签页在后台）：
  后台预检写 `rows=211 / unread=0 / peer_last=0 / candidates=0`；
  同一份列表在可见拍（13:54）是 `peer_last=16 / candidates=1`。
- 原因：这两个计数写在了“有没有活”的判定之后，而那条判定会提前结束，
  所以计数永远停在 0。这不是业务结论，是漏填。
- 现在：先把整份列表的未读与对方最后发言统计完，再判断有没有活。
  后台从此能分清三种情况：
  1. 真的没人回（整箱统计就是 0）；
  2. 有人回，但被规则挡下（会带出挡下的原因和人数）；
  3. 有人回，但读取失败（技术失败，不算对方没回）。

另外，蓝点取证从“只看会话行内部”扩展到“行内 + 父级容器”，
下次现场就能直接看出蓝点挂在哪一层，不用再靠猜。

台账里还有一种容易看错的记录：正文写成 `[未记录原文·第N轮·由台账补记，非实际发送内容]`。
它的意思是「这一轮是从历史气泡补认出来的，没有留下当时的原文」，
**不是真的发过一条消息**。看到它不要当成已发送。

**判断标准：** 后台 `peer_last` 与 `unread` 必须与列表实际一致。
如果数字是 0、而列表里明明有对方的新话，那属于反馈 bug，不算业务结论。

## 4.9.109 当前口径：先把“人”认对，再谈回不回

### 4.9.110 三条“静默丢弃”的死路已经封掉

这一版修的不是判定规则，而是**判定之前就走丢**的三条路。它们都会表现成“对方没回”，
但后台只剩一个 `unread=0`，用户查不到原因。

1. **后台标签只看到 12 行就判“没活”。**
   后台预检旧规则是“候选为 0 就不激活标签”，但候选 0 可能只是没扫全。
   现在预检必须交代数据来源：`cache_used / cache_rows / cache_age_ms / live_rows / full_list`。
   只有 `full_list` 为真才允许报 `no_task`；否则先激活标签做完整下滑扫描。
   并且 `hidden_no_work` 必须带 `drop` 与 `samples`，后台能直接看到
   “没破冰多少人 / 冷却多少人 / 谁因为什么被丢”。

2. **临时台账读失败一次就永久锁死。**
   旧规则“同一预览只尝试一次”：第一次打开碰上后台标签或白屏，就写下 `lastProbeAttemptPreview`，
   之后在预览变化前永不再打开。对方明明回了，台账里那个人永远不动。
   现在新增 `lastProbeAttemptAt`，读失败后 **10 分钟退避重试**；
   预览一变（对方真发了新消息）立即重试。等待中的单独记 `probe_retry_wait`。

3. **自愈重建标签把窗口顶到前台。**
   重建标签旧条件是“窗口本来在前台就 active”，Windows 上仍会把 Chrome 提到最前。
   现在重建一律 `active:false`，只有守箱自己发 `sg_activate_tab` 才会切前台。

**对应后台字段：**

- `chat.inbox_pulse.scan.full_list / cache_used / live_rows`：这次判定用了多少数据。
- `chat.inbox_pulse.scan.drop`、`chat.inbox_scan_drop`：每个被丢弃会话的原因与台账证据。
- `drop.probe_retry_wait`：临时台账在等退避重试，不是规则不回。

这一轮修的都不是话术，而是**身份与打开链路**。它们出错时，界面上看起来和“对方没回”一模一样。

### 1. 同一个人只能有一条有效台账

- 真实 `@handle` 一条（带破冰/广告/催加历史），临时 `p<peerId>` 一条（`round=0`）。
- 反查按证据强度挑：真实 handle、非 watchOnly、有破冰、有广告，优先。
- 打开会话拿到真实 `@handle` 后，临时记录并回真实账号（`header_adopted`），只补空缺，不覆盖已有证据。
- 已被合并的临时记录不再占用 peerId，否则真实账号回写会被挡住。

**这意味着：** 同一个人不会因为“台账里多了一条临时记录”而被永久判成没破冰。

### 2. 没真的进会话，就不允许读正文

- 路径必须带会话 id（`/i/chat/<id>`），仍停在 `/i/chat` 列表根一律不算打开。
- 没进会话 → `open_nav_failed`，本拍不读正文、不判回复、不写已读。

### 3. 缓存可以复用“有哪些行”，不能复用“读没读”

- 深扫 3 分钟一次，中间拍复用文字快照（211 行都在）。
- 但未读状态必须用当前可见 DOM 刷新；否则新蓝点亮起仍报 `unread=0`。

### 4. 后台预检不能改状态

- 标签在后台时先判断“有没有活”，没有就不激活、不抢前台。
- 预检是**只读**的：不写台账、不清冷却、不记待核对。

### 5. 拉新与守箱不能互相抢页面

- 拉新阶段（本号主页 → 粉丝列表）必须保持 `dan_chat_phase='inbox'`。
- 旧代码在这里写 `outbound`，与每 5 秒一次的守箱看门狗互相覆盖，
  关注/养号会趁机把页面抢走，破冰做到一半跳走。

### 6. OPS 记账失败要分清“真缺”和“已经补上”

- 补记链最后一步仍报 `round_gap` 时，先再读一次真实轮次；
- 已经到目标轮 → 记 `round_gap_already_recorded`，不再判失败、不再累计 `give_up`。

## 4.9.101 当前口径

### 4.9.104：状态机与旧闸门不再各说各话

- 旧台账 `round` 停在 1、但广告痕迹（`adSentAt/adBubbleOk`）已经存在时，
  旧闸门以前仍然要求 `round=2` 才允许首次催加，状态机却说可以发。
  现在两边都以“广告是否真的发过”为准：广告发过 → 允许催加；没发过 → 继续拦住。
- 台账没有 `iceSentAt` 但广告痕迹已在（补认/旧数据）时，运行时与规则镜像都返回 `ad_already_sent`，
  不会一边判“没破冰”、一边判“广告已发”。
- 文档同步纠正：非两段式破冰后**下一轮轮询就发广告**（读不出年龄按默认发），不是无限等回复。

### 后台标签：没有活就不抢前台（修「每分钟弹出来」）

以前脉冲一开头就激活 X 标签，即使用户正在别的标签页工作，也会每分钟被切回 X。
现在顺序改为：

1. 标签在后台时，先只读列表行（列表即使不渲染正文也能读）；
2. 列表里没有未读、也没有“已破冰且对方最后发言”的会话 → 记 `no_task`（`scan.reason=hidden_no_work`），
   **不激活标签、不切前台**；
3. 只有真的出现待回复会话，才激活标签；激活后仍不可见 → `page_hidden_deferred`，
   延后 20 秒，未标已读，不代表对方没回。

因此“窗口自己弹出来”只可能发生在真的有人回复时，并且最多一次。

后台标签被 Chrome 节流到 1 分钟一拍，也不再算成“系统压力”（以前会误报 `system.pressure L2`，
并跳过 DOM 扫描）；刚回到前台的第一拍同样不判压力。

### 对方关闭收件箱 = 暂停，不是永久终态（4.9.115 起）

对方关闭收件箱时，会话能读历史，但 X 不允许发送（需要对方安全码）。
这类会话不再算进“待催加”，台账里单独显示 `inbox_closed`，心跳也不会挂 1 条做不完的活。

但它**不是永久终态**：X 允许对方随时重新打开收件箱。旧实现一旦写入 `inboxClosedAt`
就再没有任何清除路径，结果是这个人从此永远不会被打开——哪怕他重开了收件箱、
甚至发来新消息，后台也只会一直显示“对方关闭了收件箱”。

现在的规则：

- 关闭时记下当时的列表预览（`inboxClosedPreview`）。
- 列表预览一变 → 立即复查（`preview_changed`）。
- 否则每 6 小时复查一次（`recheck_due`）。
- 复查时横幅已经不在了，且**身份证明通过 + 正文真的读出来** → 清除关闭状态，
  写 `inboxClosedClearedAt`，上报 `chat.inbox_reopened_by_peer`，之后按正常回复判定处理。
- 只有“没看到横幅”不足以解除：白屏/空壳同样读不到横幅。
- 关闭期间对方来的消息记 `lastInboundWhileClosedAt`，后台能回答“他明明发消息了，为什么没回”。
- 后台预检把到期复查算成“有活”，否则复查永远不会触发。
- OPS：`peer_inbox_closed_recheck`（正在复查的条数）+
  `peer_inbox_closed_samples`（handle、关闭时间、下次复查时间、预览）。
- 等输入框阶段每 1.2 秒检查一次只读横幅，命中立刻停止空等（旧版要空等满 30 秒），
  结论仍是 `peer_inbox_closed`，本拍立即换下一个目标。

### 矩阵化：单实例 CPU 占空比

每次调度 tick 的同步耗时、每次列表分类/深扫的同步耗时分别累加，60 秒心跳输出：

- `work.cpu_pct_est`：过去一分钟单核占用百分比（(tick + 列表分类/深扫) ÷ 真实间隔）；
- `work.tick_ms_avg` / `work.tick_ms_max` / `work.tick_count`；
- `work.scan_ms_avg` / `work.scan_ms_total` / `work.work_ms_total`；
- 同时保留 `heap_mb` / `dom_nodes`。

矩阵估算口径：CPU ≈ 单实例 `cpu_pct_est` × 实例数；内存按 `heap_mb` × 实例数再留 30% 余量。
真实发送/打开会话的那一拍会出现尖峰，看 `tick_ms_max` 而不是只看平均值。

## 4.9.100 当前口径（先看这里）

### 4.9.100：反馈字段必须写“真实打开方式”

以前 `chat.inbox_tick.open_mode` 只要候选带拼接地址就写成 `direct`，
即使实际是点行打开，排查时会误以为“又在整页直达”。
现在统一上报真实模式：`resume`（会话页续跑）/ `click`（点列表行）/ `row_href` / `direct`（仅人工强制）。
另外，整份列表的文字快照增加同页内存副本：`sessionStorage` 写不进去时，
下一拍仍然能覆盖 211 行，不会退回只看首屏 12 行。

### 4.9.98 / 4.9.99：先扫整张会话栏，再进会话；进不去不等于“对方没回”

**现场问题：** OPS 每一拍都是「打开了、但 0 条气泡、判定读失败」，
而页面上会话列表停在 15～18 周前，最新会话根本不在可视区。

**结论：**

1. 深扫的滚动容器以前选错，赋值“回到顶部”不生效，扫完仍停在列表底部。
   下一拍选中的新目标不在可视区 → 找不到行 → 只能整页直达会话地址 →
   X 回到列表或只画空壳 → 读 0 条气泡。
2. 整页直达 `/i/chat/<对方>-<本号>` 在这个账号上不可用，**不再作为正常打开方式**。
   只有人工强制测试才允许直达。
3. 深扫改为 3 分钟一次；中间的每一拍读纯文字快照，仍然覆盖整份 211 条列表。
   所以“先处理对方回复的、再处理我已回复的”这个顺序不变，也不会因为不滚屏而漏人。
4. 找不到行时给结论 `deep_row_gone`（深度扫描见过、当前列表找不回），
   90 秒内跳过该目标；**不再算成 `reply_read_failed`，也不算对方没回**。
5. 文字快照必须保留换行。4.9.98 第一版把「显示名 / 时间 / 预览」压成一行，
   快照拍会把 211 行全部判成 `unknown`、0 候选，等于整箱都漏；
   4.9.99 逐行规范化后再拼接，实测恢复为 `peer=19 / own=192 / unknown=0`。

**打开会话的固定顺序：**

1. 当前可见行 → 直接点行；
2. 不可见但列表里有 → 用验证过的滚动容器滚到该行，再点；
3. 滚完整张列表仍找不到 → `deep_row_gone`，换下一个目标；
4. 只有人工 Force 测试才允许整页直达。

**OPS 能直接看到的证据：**

- `chat.inbox_pulse.scroller`：真实滚动容器的 tag / testid / scroll_top / scroll_height；
- `scan.scroll.topResetOk`：深扫后是否真的回到顶部；
- `scan.scroll.scrollerVerified`：滚动容器是否通过“能被 scrollTop 移动”实测；
- `deep_row_gone`：列表里找不回该行，不是回复检测失败。

### 4.9.97：换页后引擎不能“失联”

拉新阶段要回本号主页读粉丝数。如果这一跳之后主引擎没恢复，OPS 上会出现
「页面在、`last_pulse_at` 却停住、`next_pulse_in_ms=0`」的情况，看起来像“引擎在但没检测”。

现在有一个独立的看门狗（不依赖主引擎）：

- 拉新阶段停留超过 90 秒 → 复位回守箱，并导航回 `/i/chat`；
- 守箱脉冲逾期超过 3 分钟 → 主引擎在就唤醒，不在就回列表页重载；
- 两次导航至少隔 2 分钟，避免来回跳；
- 每次动作都写 `chat.engine_watchdog`，能直接看到是谁把引擎救回来的。

### 4.9.96：没有 @handle 的临时会话不能一直重复打开

列表里有些会话行拿不到 @handle，只能用数字 peerId 建临时台账。这类会话如果打开后是空壳
（读不到正文、证明不了身份），过去会每 60–90 秒重开一次，永远循环，把真正有回复的人挤到后面。

现在：

- 读失败记下“这次试过的列表预览”，同一预览最多再试一次；之后只有预览变化（对方真来了新消息）才重新探测。
- 读成功才记“已核对预览”，不会因为一次读失败把真实回复永久跳过。
- 这类失败仍然单独上报（`reply_read_failed` / `identity_pending`），不会伪装成“对方没回”。

### 4.9.95：已完结会话不能因为“历史气泡”被重新打开一轮

**现场问题：** 一个已在 08:22 收口的会话，08:25 又被判“对方收口后又来信”，重新发了一次广告，
轮次从 3 回到 2，08:27 又开始催加。同一个人 5 分钟内收到 4 条消息，广告是重复的。

**原因：**

1. “有回复”原来的含义是「会话里存在对方气泡」，而不是「收口后对方又说了新话」。
   已完结会话里历史消息一直都在，所以一打开就必然判成有回复。
2. 旧台账的 `closedInboundNoReply` 被当成复活理由，它的本意其实是「已核对过、没有新回复」。
3. 扫描阶段会写“待核对”时间戳，如果不校验真实入站，这个标记会自己给自己续命。

**现在的规则：**

- 收口后要复活，必须有真实新入站证据：对方入站时间/回复时间晚于收口时间，或列表上有精确未读。
- 打开读完以后，如果最后一条仍是我方 → 结论 `reopen_no_new_peer_last`，**不重发广告**，本次来信结案。
- 打开读完以后，最后一条确实是对方 → 才按广告段重新分流（年龄合格发广告 / 不合格婉拒）。
- 硬封（已婉拒 / 已拉黑）任何情况下都不复活。

### 4.9.90–4.9.94 修掉的五类“看起来像漏回”的问题

1. **深度下滑（4.9.90）**
   旧逻辑只扫列表顶部十几行，后面的会话永远轮不到。现在会真的滑到底，扫描明细写 `rows / stopped_reason=bottom_reached`；
   只有完整扫到底的结果才允许用来做“这个会话不在收件箱”的判断。

2. **临时台账被误判（4.9.90 / 4.9.91）**
   以前用“名字像 p+数字”来认定临时台账，真实账号 `p89089212` 被误伤。现在只认显式标记 `watchOnly` 或 `dn_` 前缀。
   核对也改为按证据触发：有未读或列表预览变化才打开；同一预览只核对一次；读失败不记“已核对”。

3. **我方文案被当成对方回复（4.9.92）**
   X 有时不给自己的消息加“你:”前缀，列表预览会把我们发过的广告/催加文案当成“对方最后一句”。
   现在只和台账里真实记录过的 `lastAdText / lastKick1Text / lastFinalKickText` 比对，命中即认定是我方，不再误判成新回复。
   同时 `applyInboxSendResult` 的广告分支会写入 `lastAdText`，从源头保证可比对。

4. **历史破冰被重复发广告（4.9.92）**
   补认破冰时，如果会话里已有含 `line.me` / `LINE ID` 的我方气泡，直接补认 `adSentAt` 与 `round≥2`，不会再发一遍广告。

5. **台账有、收件箱里找不到，永远挂着（4.9.93）**
   现在按“完整扫描次数”收口：连续 12 次真的扫到底都没出现、且距破冰超过 24 小时，才写
   `closedWhy=conversation_not_in_inbox`，并给出中文原因。只扫顶部的一拍不计数，避免误杀。
   扫描明细新增 `not_seen_in_list / not_seen_closed`，能直接看出“为什么这条一直挂在待处理”。

### 4.9.94：OPS 补记失败不再每 4 分钟刷屏

本地台账轮次比 OPS 高时要补记。过去同一个目标补不进去（例如 OPS 缺前轮、早期轮次不可重建）会永久重试，
每 4 分钟报一次 `chat.inbox_ledger_reconcile_fail`，日志被同一条淹没。

现在：同一目标失败累计到 5 次即隔离，写 `opsReconcileGiveUpAt / opsReconcileGiveUpReason`，
只上报一条 `reason=gave_up`（带 `last_reason` 与 `attempts`），之后不再排队重试。
补记仍然只改 OPS 轮次，不发任何消息。

### 4.9.84 / 4.9.85 修掉的三个“假不回复”

1. **地址对了但正文是空壳（4.9.84）**
   按对方数字 ID 整页直达 `/i/chat/<对方>-<本号>` 时，X 有时只渲染左边列表、右边停在“开始对话”。
   旧逻辑只看输入框/会话头就认为“已打开”，下一拍读到 0 条气泡 → `reply_read_failed`，并冷却 30 分钟。
   现在：台账明明发过消息却一条气泡都读不到 = 没渲染，本拍改回**点击列表行**重开（事件 `chat.inbox_resume_empty`）。

2. **读不到正文被当成“对方先私信”（4.9.84）**
   页面没渲染时，我方气泡数当然也是 0。旧逻辑据此写 `peerDmBeforeIceAt`（判定为陌生人先来私信），
   这条会话就被永久跳过。现在只有**真正渲染出气泡**时才允许下这个结论；之后读到我方气泡会清掉旧结论。

3. **收口会话每拍空转“复活”（4.9.85）**
   旧台账里带“收口后有未核对来信”标记的会话，会被每一拍重新复活；打开后读到的却是“最后一条是我方”，
   于是永远占着队首。现在复活一次且读回“没有新发言”后，记下列表预览；30 分钟内预览没变就不再复活，
   预览一变（对方真来了新消息）立刻恢复。丢弃原因进 OPS：`drop.revive_cooldown`。

### 临时台账不再永久丢弃（4.9.84）

`p<对方数字ID>` 这类“没有 @handle 时探测过一次”的临时台账，旧逻辑无条件丢弃。
现在：对方最后发言 +（有未读 或 列表预览变了）时允许带预算重新核对，最多 3 次。
核对时若会话里有我方气泡 → 补认破冰，继续年龄/广告/催加；没有我方气泡 → 明确不发送。

### 私信只有两个阶段

1. **拉新（粉丝列表）**：定时回本号主页读粉丝数。只有涨粉才进粉丝列表登记、排队破冰；没涨只记录并回守箱。
   破冰只有这一个入口，守箱永远不补破冰。
2. **守箱（私信列表）**：只处理已破冰的会话——读回复、判年龄、发广告、按轮次催加。

### 非两段式（约会池）

- 破冰发出后，**下一次轮询就发广告**，不再空等 60 分钟。
- 对方有回复：先判年龄。低于门槛 → 婉拒并立即完结；合格 → 发广告。
- 读不出年龄：按规则默认发广告，原因记 `age_unknown_ad`。
- 广告后：第一次催加、第二次终催；两次都按“下一次轮询”推进，发完终催即完结。
- 完结后对方又来信：必须是“最后一条确实是对方”的新入站，才按广告段重新分流（年龄合格发广告 / 不合格婉拒）；
  只是历史气泡、最后一条仍是我方 → 不重发，记 `reopen_no_new_peer_last`。

### 两段式（兼职/job 池按意向）

- 破冰 → 等待对方回复或满等待期 → 发含 LINE 的第 2 段 → 直接完结，不再催加。

### 老会话历史校准（4.9.79 起）

- 名册首次建账会把老粉写成 `round=0`。守箱看到“台账没破冰、但列表最后一条是对方”时，允许打开一次核对历史。
- 会话里已有我方气泡 → 补认破冰（`ice_adopted`），继续按年龄/广告/催加处理。
- 会话里没有任何我方气泡 → 记 `peer_dm_before_ice`，明确不发（破冰只能走粉丝列表）。
- `p<peerId>` / `dn_<显示名>` 这类合成键不是真实粉丝，不做历史校准。

### 什么时候“正常不回复”

- 没破冰（`ice_via_roster_only` / `peer_dm_before_ice`）
- 已婉拒（`rejectSentAt`）或已拉黑（`blockedAt`）
- 已完结（`chatClosedAt` / `finalKickSentAt` / `round≥3`）且没有收口后新入站
- 对方关闭收件箱（`peer_inbox_closed`，需对方安全码；本次不发，预览变化或满 6 小时会复查，对方重开即恢复）
- 非私信时段（夜间不做任何私信动作）
- 冷却中（渲染失败 / 身份未证明 / 目标跳过）
- 复活冷却中（`revive_cooldown_same_preview`：同一预览 30 分钟内已核对过，且确实没有新发言）
- 台账有、但连续多次完整扫描都不在收件箱（`conversation_not_in_inbox`：会话可能已删/对方注销/入口变更）
- 读不到正文（`reply_read_failed`）——这是技术未读成功，不算“对方没回”，下一次会换目标重试

### 技术失败必须可区分

- `reply_read_failed`：会话正文没读出来，**不代表对方没回**，禁止发送、禁止写“已读”。
- `identity_pending`：没证明打开的是目标本人，禁止发送。
- `page_hidden_deferred`：标签页在后台，本拍不打开、不判定。
- `open_direct_nav` / `nav_budget_wait`：正在换页或跳转冷却，不是对方没回。

### 反馈字段

- `chat.inbox_scan_drop`：谁被扫到但没处理、为什么、台账证据（单独事件，避免主事件被截断）。
- `chat.inbox_tick`：`reply_verdict / reply_reason / send_gate / send_error / ice_adopted / identity_reason`。
- `chat.inbox_pulse`：本拍扫描行数、候选数、打开谁、结论、下一次时间。

## 4.9.52 这一轮改了什么（先看这里）

1. **收口后对方又回复 = 新的一轮，不再“只标已读”**
   - 旧逻辑：收口会话读到新消息后写了“已处理”，但动作判定一律 `stage_closed`，什么也没发；
     下一拍就判 `already_surfaced`，这条回复永久消失。
   - 现在：收口后出现真入站（`inbound_after_close / peer_last_after_close / precise_unread_after_close`）
     → 按广告段重新分流：年龄合格发广告，年龄不合格发婉拒；广告发出后清掉终催/收口标记，重新走“广告 → 两次催加”。
   - 读到回复但**没发出去**（无联系方式、输入框失败、业务闸门）→ 不写“已处理”，下一拍继续。
   - 真婉拒（`rejectSentAt`）与拉黑（`blockedAt`）永远不会被复活。

2. **催加节奏 = 下一次轮询**
   - 默认两次催加之间至少 60 秒（一拍），对应 `chat_inbox_kick_min_minutes=1`。
   - 积压排水是 8 秒一拍，旧默认 0 会让“首次催加 + 终催”在几十秒内连发；现在不会。

3. **脉冲真的下滑**
   - 扫描节流阈值从 55 秒降到 30 秒。旧值几乎等于 60 秒脉冲间隔，现场每拍都 `deep_scan_throttled`、`scrolledPx=0`。
   - OPS `scan.peerLast` 改为统计整张列表里“最后一句是对方”的行数，不再只看候选（旧口径会出现 `lastSpeakerCounts.peer=31` 但 `peerLast=0` 的矛盾）。
   - 深度扫描选中的目标滚出首屏时，仍会用快照滚回去点击；不再因为“当前 12 行没有候选”整拍放弃（`no_actionable_rows`）。

4. **广告/催加的底线是“有 LINE 联系方式”，不是“必须有 line.me 链接”**
   - 线上话术池同时存在 `{LINK}` URL 和「LINE ID：@xxx」「LINEで待ってるね」两种写法；
     只认 URL 会把整条私信链路静默停掉。
   - 完全没有联系方式时才 `send_error=no_promo_link`，并带中文原因。

5. **不再强行弹出 Chrome**
   - 窗口最小化时不再 `windows.update(state:'normal')` 替用户还原；直接记 `page_minimized_deferred`，等用户自己恢复。
   - 标签页在后台时只激活窗口内的标签，不抢窗口焦点。

6. **OPS 轮次**
   - 收口复活后的第二轮对话继续排 `5/6/7`（再次广告 / 首次催加 / 终催），
     不再和上一轮的 `2/3/4` 撞唯一键被吞掉。

## 先说明一个不是“回复判定”的问题：窗口为什么自己弹出来

4.9.38 修掉了现场最扰人的一条：插件会把 Chrome 窗口反复顶到前台。

原因不是弹提醒，而是两条“自愈”叠加：

1. 守箱每拍要激活标签页，旧版会连带请求“把窗口拿到前台”。
2. 标签页在后台时 X 不渲染正文，插件把“看不见”误判成“白屏”，于是请求自愈；
   自愈升级到重建标签页时，新建标签会激活窗口 → 窗口被顶到前台。
   新页仍在后台 → 又被判白屏 → 再重建，形成循环。

现在的规则：

- **后台标签页一律不算白屏**，不做任何自愈，只记 `page_hidden_deferred`（标签在后台，本拍延后）。
- 激活只激活窗口内的标签，**不抢窗口焦点**。
- 重建标签页只在窗口本来就在前台时激活新页，否则后台新建。
- 空白页恢复顺序：先站内软跳 `/home` → 再软跳回 `/i/chat`（不刷新）；
  连续 2 次无效才整页刷新；刷新预算用尽后每 3 分钟仍允许一次保底重试；
  仍空白就整页换 `/home` 重置路由。**不会再有“预算用尽后整段时间不动”的静默状态。**

私信从 4.9.0 起拆成两个阶段，4.9.1 补齐三条产品口径，由同一个调度循环驱动：

- **拉新（roster）**：定时回本号主页读粉丝数。数字涨了才进粉丝列表登记新粉、排队破冰；没涨只记录，马上回守箱。**破冰只有这一个入口。**
- **守箱（watch）**：只处理已经破冰的会话——读回复、判年龄、发广告、按轮次催加。

所以“守箱里为什么不发破冰”不是漏了，是业务规则：没破冰的会话不在守箱处理范围内（`ice_via_roster_only`）。

### 两阶段的循环规则

守箱不是一直盯着 DM。每隔一段时间（默认 30 分钟，`sg_roster_check_min` 可调 5–360 分钟），
在不忙、没有待重试发送时，切去拉新：

1. 回**本号资料主页**读粉丝数（只在主页读；粉丝列表页的数字不可信）。
2. 读不到数字 → 停在主页重试，绝不带着 0 去扫列表。
3. 和台账基线比较：
   - **没涨粉** → 只记一次 `no_growth`，立刻回守箱，不滚列表。
   - **掉粉** → 只把基线下调到本次读数，已有台账不动，回守箱。
   - **涨粉** → 进粉丝列表，登记新粉、排队破冰；扫完把基线对齐到本次读数。
   - **还欠破冰** → 先清队列（`drain_ice`），再按上面的规则查数。
   - **没有基线（首扫）** → 只全量登记台账，**不排队破冰、不发任何私信**。存量粉丝从此只留在台账里，破冰只针对“基线之后新回关的人”。
     要让存量粉丝也补破冰，必须显式设置 `sg_roster_first_scan_ice = all`；默认 `ledger` 就是“只建台账”。
4. 进粉丝列表后只做**破冰**：广告、催加一律标成 `deferred / handled_in_watch`，交给守箱。避免粉丝列表把广告/催加抢在破冰前头发掉。
   - 队列里还有待做的破冰时，新粉先写台账、不抢队；队列一空，下一轮涨粉就会把新粉排进去。
   - 连续 7 天没在粉丝列表里再出现的未破冰目标，视作已取关（`left_followers`），不再算破冰债，避免永久挡住新粉。
5. 队列做完 / 到每日上限 / 到收工条件 → 自动回守箱（不会走旧的“回关注/结束软窗”逻辑）。

整个过程 `sg_run_mode` 始终是 `inbox`，不会因为切换阶段把守箱开关关掉。

## 一、一条新消息进来后，系统按什么顺序判断

1. **收件箱列表有没有信号**
   - 台账里没有破冰记录（`iceSentAt`）的会话一律不打开，计入 `scan_drop.noIce`。破冰只能从粉丝列表发起。
   - 列表行先判“最后一条是谁说的”，再看台账：
     1. **对方最后发言 + 未读** → 最高优先级，先打开回复。
     2. **对方最后发言（已读但未处理）** → 第二优先级，仍要打开。
     3. **我方最后发言** → 视为已经回复过；只有台账有到期动作（广告债/催加）才打开。
     4. **只有我方草稿** → 不算对方发言，不因此打开。
     5. **列表预览读不出** → 只有未读、台账到期动作、探测到期才打开。
   - 台账 `replySeenAt` 只是“历史上读到过回复”的记录，**不能压过列表证据**。列表明确显示最后一条是我方时，不会因为台账没记全就反复打开、反复标已读。
   - 三类都没有 → 不打开：`ownLastReplied`（我方最后、视为已回复）、`unknownPreview`（读不到预览且无到期动作）、`notActionable`（无未读、无台账待办）。这是正常的“没有新任务”，不是技术故障。

   **草稿不算对方发言。** 列表行里的“草稿：…”是我方未发出的内容，既不算入站信号，也不能当成对方最后一句。判断“对方是否最后发言”时会同时排除我方已发出的预览和待发草稿，避免把自言自语当成对方回复。

   **脉冲必须真的下滑。** 会话栏是虚拟列表，只扫当前可见的十几行会漏掉下面的人。4.9.12 起每一拍（默认 60 秒）都会在列表自己的滚动容器里向下滚，边滚边冻结行快照；找不到可滚容器时用行级 `scrollIntoView` + 滚轮兜底。OPS 的 `chat.inbox_pulse.scan.scroll` 会给出 `steps / scrolledPx / rowsBefore / rowsAfter / uniqueRows / reachedBottom / stoppedReason / scrollMode`。看到 `steps=0` 且 `stoppedReason=scroll_not_moved` 才是真的没滑动；看到 `bottom_reached` 是已经到底，不是漏扫。

   **标签页在后台时先激活标签，但绝不抢窗口焦点。** X 在后台标签页不渲染会话正文，虚拟列表也只挂载几行；这时扫描/下滑会得到“只有 9 行”的假结果。脉冲先激活窗口内的标签（`chrome.tabs.update`），确认 `visible` 之后才扫描、下滑、打开会话。**窗口最小化时不还原窗口**，直接记 `page_minimized_deferred`，等用户自己恢复；否则现场就是 Chrome 每隔几十秒自己弹出来。hidden 时 20 秒后重试，而不是等满一整拍。OPS 的 `hidden / activated_tab / tab_active / window_state / activation_reason / hidden_alert` 能看出卡在哪一步；hidden 时 `scan.skipped=page_hidden`，不会再把后台空壳当成完整列表。首次从 hidden 转 visible 时会清一次 `renderFailCount` / `identityPendingCount`（`render_reset / identity_reset`），因为那些失败通常是后台不渲染造成的，不该让目标白等 30 分钟。

   **滚动后不会再串号。** 虚拟列表会复用同一批 DOM 行；如果只保存行对象，滚走后那一行可能已经换成别人。现在首次看到时就冻结 `id / href / 预览 / 未读`，之后排序和打开都按冻结快照走。列表里“谁最后发言”因此不会因为滚动而错位。

2. **能不能证明打开的是目标本人**
   - 会话头 handle 与目标一致，或 URL 的对方 ID 与台账一致 → 通过。
   - 新版 `/i/chat` 的会话头在 shadow DOM 里：只认“消息区上方、非气泡内、非导航栏、非本号”的对方资料链接（`header_source=panel_header`）。`main` 兜底只算低可信线索，不能单独判“点错人”，否则会把导航栏里的本号误当会话对象。
   - 两者都证明不了 → `identity_pending`，本拍不发，等下一拍。**这是技术保护，不是对方没回。**
   - 打开的人与台账里记录的 peerId 不是同一个 → `peer_id_mismatch`，本拍不发（防止发错人）；只有会话头明确证明是目标本人时，才允许以会话头为准修复台账并留痕 `peerIdRepairedAt`。
   - 连续 2 拍都证明不了身份 → 冷却 30 分钟（`identity_unverifiable_cooling`）；**未读也不能绕过**。列表预览发生变化时立即解除冷却并重试。这是为了保证一个身份错配的会话不会每拍霸占队首，把后面的人永远挤掉。
   - 连续 3 拍以上都证明不了身份 → 告警级别升为 `error`（`identity_alert = identity_unverifiable_repeated`），OPS 能直接看到，不再只是“没动静”。
   - 身份没证明时，页面上读到的回复**不会写进台账**（只记 `identityBlockedAt`），避免把别人的消息记到目标头上。

3. **会话正文读到了什么**
   - 读到对方文本 → 进入回复判定。
   - 只有气泡、没有文字（图片/贴纸/语音）→ `peer_non_text_unhandled`，记录“对方发来非文本消息”，不冒充“没回复”。
   - 连气泡都没有、会话头也没有 → `dom_empty`，判为页面没渲染，刷新重试，不判“没回复”。

4. **按台账阶段决定发不发**
   - 还没破冰 → 不发（`ice_via_roster_only`）。破冰只能在拉新阶段从粉丝列表点进主页后发出，守箱不补、也不因为对方先来信就发广告。
   - 已破冰、对方有回复 → 发广告；年龄低于门槛 → 发婉拒；job 明确拒绝 → 发婉拒。
   - 已破冰、没有回复、两段式等待期未满 → 等。
   - 已破冰、没有回复、两段式等待期满 → 发第二段（含 LINE）。
   - 已发 LINE（两段式完成）→ 业务完结，不再回复。
   - 非两段式：广告之后不再做别的判断，只按间隔催加两次（详见下一节）。
   - 已婉拒 / 已拉黑 / 对方明确拒绝 / 对方已封我们 → 不再回复。

   **收口后来信**：列表先记录未读/最后发言证据；硬拒绝或拉黑仍不处理。普通收口会话出现新入站时，必须打开读取正文，再交给现有状态机判定；不得在列表层写 `closedInboundNoReply` 后直接丢弃。状态机若判定两段式广告已完成或催加轮次已结束，会明确记录 `stage_closed`，不会重复发送旧广告。旧版遗留的 `closedInboundNoReply` 若从未实际打开检查，会作为待检查记录恢复一次，读取成功后写 `closedInboundCheckedAt`。

   **复活会话必须真的被脉冲选中。** 4.9.22 修掉了一个致命分叉：候选排序会给 `revived` 最高优先级，但脉冲选目标时又用 `closed=true` 把它跳过，结果“列表有未读、台账也记了待检查，却永远不打开”。现在只有“收口且没有复活”的会话才跳过；已复活的会话会正常打开、读正文、再由状态机决定发不发。

   **整页刷新有硬预算。** 打开会话优先点列表行走 SPA；地址直达和点击失败后的整页跳转都限制为 60 分钟内最多 1 次、最小间隔 5 分钟。超限只记录 `nav_suppressed`，不会用反复刷新来“碰运气”。刷新多不等于处理多；每一拍的结果以 `chat.inbox_tick` 的回复结论为准。

   **尾斜杠不再整页卸载。** 从会话页回列表时如果地址变成 `/i/chat/`，旧逻辑会用整页跳转纠正，页面会直接卸载、心跳中断。4.9.23 改为只改地址并通知前端路由（`slash_route_fix`），5 秒后继续下一拍；页面重新加载后也会自动收回旧版本留下的 5–10 分钟长退避。

   **回列表必须点真实返回。** 4.9.24 起，处理完会话不再用 `pushState` 直接改地址回列表，而是先点 X 会话页的返回按钮，再退而求其次用 `history.back()`；只有前两者都不可用时才软跳地址。原因是只改地址不会让 X 重绘列表，下一拍会看到 0 行，随后刷新预算耗尽、页面停在空白列表。事件里的 `return_mode` 会记录本次实际用了哪种方式。

   **回列表异常不能再中断整拍。** 4.9.24 曾把回列表结果写到不存在的 `result` 变量，导致 `pulse_exception` / `result is not defined`，`rinzkumk9` 因此没有被处理。4.9.25 改为写入 tick 的返回对象，再由脉冲层平铺到事件；出现异常也必须留下可检索的错误原文，不能表现成“没轮到”。

   **扫描不等于已处理。** 4.9.26 起，扫描阶段只登记“待检查”（`closedInboundPendingAt`），不会写 `reopenedAt`。只有会话真正打开、身份确认、正文读到之后，才把 `reopenedAt` 写成“已处理”。这样任何一步异常都不会把目标永久标成 `already_surfaced`；异常会保留 pending、记录崩在哪一步，并在 5 秒后重试。

   同理，“已核对” `closedInboundCheckedAt` 也推迟到整拍末尾才写：必须等判定、发送、回列表、`chat.inbox_tick` 上报都走完。旧版在读到正文时提前写，导致 `rinzkumk9` 这类目标在回列表异常后被永久跳过。4.9.26 还用 `sg_inbox_recheck_closed_inbound_v4926` 做了一次性迁移，把旧标记清掉重新核对一次。

   **对方只发非文本**（图片/贴纸/语音）时没有可判定文本，结论固定为 `peer_non_text_unhandled`，并单独上报 `chat.inbox_non_text`；台账写 `lastNonTextInboundAt`，不会被当成“没回复”。

5. **发送后写台账**
   - 成功：推进轮次、写发送时间。
   - 失败：保留待办，下一拍重试；同时把失败原因写进 OPS。

**下滑找不到容器时怎么办：** 先同时从第一行、最后一行、listbox 三条祖先链找 `overflow:auto/scroll`；仍找不到就让最后一行 `scrollIntoView` 并补一次滚轮事件。OPS 的 `scan.scroll.scrollMode` 会写 `scroll_into_view`，`scrollCandidates` 会列出候选节点的 `tag / testid / overflowY / scrollHeight / clientHeight`。看到 `no_scroll_container` 时，下一步就是根据这些候选值确认页面是不是换了滚动实现。

**直开会话后为什么不再回列表：** 整页跳转偶尔会丢 `sessionStorage.pending`。现在只要 URL 是 `/i/chat/<peer>-<my>`，就会用 URL 的 peerId 反查台账并重建待办（`reconstructed=true`），继续读取这个会话；`chat.inbox_loop.pending` 会显示待办的 handle / peer_id / tries / age_ms。不会再出现“直开→回列表→再直开同一个会话”的空转。

## 二、非两段式的完整判断顺序（重点）

非两段式（约会池 / 经典模式）只有一件事能改变路线：**年龄**。除此之外，广告之后全部是催加。

| 顺序 | 当前状态 | 动作 | OPS 里的结论 |
|---|---|---|---|
| 0 | 台账没有 `iceSentAt`（还没破冰） | 守箱一律不发，交回拉新阶段从粉丝列表破冰 | `ice_via_roster_only` |
| 1 | 已破冰（拉新阶段在粉丝列表发出，台账有 `iceSentAt`） | 进入下面的广告/催加判定 | — |
| 2 | 已破冰、广告未发、没有对方文本 | 什么都不发，只等 | `await_reply` |
| 3 | 已破冰、广告未发、有对方文本 | 唯一判定年龄：低于门槛 → 婉拒；否则发广告 | `age_below_N` / `age_ok` / `reply` |
| 4 | 广告就是在本轮轮询里发的 | 本轮不再对它做任何动作 | `kick_wait`（`next_round=true`） |
| 5 | 下一轮轮询轮到它（队列里没有更优先的会话） | 发第一次催加（含 LINE） | `kick_ready` |
| 6 | 第一次催加就是在本轮发的 | 本轮不再动作 | `kick_wait` |
| 7 | 再下一轮轮询轮到它 | 发终催，并写 `finalKickSentAt` / `chatClosedAt` 收口 | `kick_ready` |
| 8 | 已收口（婉拒 / 拉黑 / 终催 / round=3） | 永不再发，也不打开会话（不制造已读不回） | `stage_closed` |
| 9 | 已收口，且对方在收口后又发来新消息 | 先打开读取正文，再交回本表的既有判定；同一批消息只处理一次，硬拒绝/拉黑除外 | `revived_reason=precise_unread_after_close / inbound_after_close / reply_after_close / peer_last_changed` |

五条硬规则：

- **年龄是唯一分流。** 年龄没解析出来 = 不算低龄 = 照常发广告，但原因单独记成 `age_unknown_ad`（OPS 同时带 `age_known=false`），不和“读出了合格年龄”混在一起。
- **广告之后不看对方说了什么。** 无论对方回“谢谢”“20岁”还是“不要”，都不会改路线，只按间隔发催加；两次催加后收口。
- **破冰后没回复，也会在下一轮轮询发广告。** 业务口径是“非两段式只判年龄，读不出年龄就按默认发广告”，所以不会无限等回复；广告发出后才进入催加。等待的这一轮里只做低频探测，48 小时仍无入站按第六节规则处理。
- **催加由轮询轮次决定，不按固定分钟数。** 同一轮轮询只对同一会话做一步：广告在第 A 轮发，第一次催加要等 A 之后的下一轮轮询到它；终催再等一轮。**到点的广告债 / 催加会豁免 8 分钟会话复查冷却**，所以“下一轮轮询”是真的下一轮（默认脉冲 60 秒），不会被复查冷却拖成 8 分钟。想放慢，OPS 填 `chat_inbox_kick_min_minutes` 作为额外时间底线（默认 0 = 不加；终催可单独用 `chat_inbox_final_kick_min_minutes`）。诊断里的 `cycle.kickCadenceMin / revisitCooldownMin / kickBypassRevisitCooldown` 直接显示当前口径。
- **阶段只看发送痕迹。** 判断走到哪一步，只看有没有 `iceSentAt`（破冰）、`adSentAt`（广告）、`kickCount/kickSentAt`（催加）；`round` 只是结果，不参与判断。所以即使台账里的 `round` 和发送记录对不上，也不会因此发错或停住。

两段式对照：破冰 →（有回复，或等待期满）→ 发含 LINE 的第二段 → 立即收口，不再催加。所以两段式没有第 4~7 步。

## 三、哪些是「正常不回复」

这些是业务规则，不是程序坏了：

- 两段式已经发出 LINE，主动收口，不再追聊。
- 已发婉拒、已拉黑、对方明确说不要、对方已封我们。
- 对方年龄低于门槛，已发婉拒。
- 还没破冰的会话在守箱里不处理（`ice_via_roster_only`）：破冰要等拉新阶段从粉丝列表发起。
- 存量粉丝（建基线之前就在台账里）默认不补破冰（`baseline_seed`）；连续 7 天没在粉丝列表出现的目标按已取关处理（`left_followers`）。
- 还没到下次查数时间（`not_due`）、本号主页读不到粉丝数（`count_unreadable`，停在主页重试）。
- **非私信时段（默认 09:00–18:00，OPS 账号级可覆盖）**：生产/主线守箱完全暂停，不扫列表、不打开会话、不发任何私信（`outside_chat_hours`）。夜间只跑关注、养号、手动转帖。**测试副本 4.9.12 默认 `test_24h=true`，为了现场验收不按这个时段暂停；显式 `sg_test_24h=false` 才恢复真实时段。**
- 粉丝数没涨（`no_growth`）或掉粉（`count_down`）：只记录/下调基线，不滚粉丝列表。
- 两段式：破冰后还在等待期内（默认 60 分钟）且对方没回，暂不发第二段。
- 非两段式：刚破冰、还没到下一轮轮询（默认 60 秒一拍），本拍等下一轮（`await_reply`）；下一轮就会发广告，不会无限等。
- 非两段式：广告或上一次催加就是本轮发的，正在等下一轮轮询轮到它（`kick_wait`、`next_round=true`）。
- 已收口（婉拒 / 终催 / 拉黑）后对方又来信：普通收口会重新打开读取正文，再交给同一套状态机判定（年龄合格发新广告、低龄发婉拒）；只有婉拒/拉黑这类硬收口永不复活。
- 对方没有任何新消息，且台账没有待办。
- 到达每日私信上限、非私信时段、账号冻结、SCRM 未放行、舰队槽满、软风控。
- 48 小时内没有任何入站证据，**且确实完整扫过该会话**，才按超时目标清理；没有扫描证据的只延后，不拉黑。

## 四、哪些是「技术失败」，绝不能再冒充「对方没回」

| 现象 | 现在的结论 | 处理 |
|---|---|---|
| 会话正文读不出（0 气泡/0 文章） | `reply_read_failed` | 技术失败，禁止发送、禁止写“已读”；换下一个目标，不判对方没回复 |
| 读到气泡但最后一条方向无法确认 | `direction_unproven` | 技术未判明；不能当作对方回复，也不能当作我方已回复；禁止发送并上报方向计数 |
| 点击后 URL 没变/没进会话 | `open_nav_failed` | 改用 peerId 地址直开一次；仍失败记 `open_unreachable`，不再整页刷新 |
| 打开后证明不了身份 | `identity_pending` | 本拍不发，不拉黑 |
| 看到未读但正文没解析出来 | `unread_only` + `unreadSeenAt` | 记为入站证据，48h 清理不得误杀 |
| 对方只发图片/贴纸/语音 | `peer_non_text_unhandled` | 明确记录，不能当成空会话 |
| 发送没确认 | `send_error` / `send_confirm_reason` | 保留待办，下一拍重试 |
| 列表行匹配不到 | `row_not_found` / `no_actionable_rows` | 记录原因，不静默跳过 |
| 会话已收口，之后对方又来消息 | `revived_reason=precise_unread_after_close / inbound_after_close / reply_after_close / peer_last_changed` | 必须打开读取正文，再交回同一套状态机判定；同一批旧消息只处理一次，硬婉拒/拉黑不复活 |
| 收口后来信的旧消息已记录过 | `already_surfaced` | 不重复记录；有新入站才会再次触发 |
| 对方只发图片/贴纸/语音 | `peer_non_text_unhandled` | 无文本可判定，单独上报 `chat.inbox_non_text` |
| 列表最后一条是我方草稿 | `draftOnly`（不算入站） | 不打开、不复活的正常原因，不是对方没回 |
| 列表最后一条是我方已发出消息 | `scan_drop.ownLastReplied`（`own_last_already_replied`） | 视为已经回复过；没有广告/催加到期动作就不打开 |
| 列表读不到预览（只有名字/时间） | `scan_drop.unknownPreview`（`preview_unknown`） | 无未读、无到期动作就不打开；有未读/到期动作仍会打开 |
| 台账没破冰却出现在收件箱 | `ice_via_roster_only` + `scan_drop.noIce` | 记录原因，不打开；破冰改由拉新阶段从粉丝列表发起 |
| 本号主页粉丝数读不到 | `count_unreadable` | 停在主页重试；连续读不到才回守箱，不带着 0 扫列表 |
| 不在私信时段（生产） | `outside_chat_hours` | 业务规则：守箱暂停，不打开会话、不发消息；夜间交给关注/养号/手动转帖。测试副本 4.9.12 默认 24h，不受此条限制 |

## 五、发送失败与待办重试

- 发送未确认（`send_error` / `send_confirm_reason`）时，目标会保留为 `pending`，不会当成已发送。
- 下一拍优先续跑这个待办，即使列表里出现了别的未读会话，也不会把它顶掉（`pending_resume`）。
- 同一目标连续 3 次仍发不出去 → 明确放弃，写 `sendAbandonedAt / sendAbandonedReason = retry_exhausted`，并上报 `chat.inbox_task_abandoned`。
- 待办超过 3 分钟、或打开的会话与待办对不上 → 同样明确放弃（`pending_expired` / `pending_target_mismatch`），不允许静默消失。
- 重试次数不会因为一次页面恢复被重置；否则会无限重试，永远到不了“放弃并交回调度”。

## 六、48 小时清理的保护条件

只有同时满足以下条件才会清理：

- 轮次在 1~2，未完结、未拉黑；
- 距最近一次我方消息已满 48 小时；
- **最近一次我方消息之后没有** `lastInboundAt`、`replySeenAt`、`unreadSeenAt`、`lastNonTextInboundAt`；
- **必须真有“我方最后一条之后完整读过会话”的证据**（`inboxWatchedAt` 或 `conversationScannedAt` 晚于我方最后一条）。
- 白屏、一条气泡都没有的空壳、身份未证明，都不算“读过”，不会写扫描证据。
- 会话里只有我方破冰/广告、没有对方消息，但只要页面确实渲染出了气泡，就算“读过”——否则“发了没人回”的目标永远攒不到证据，48h 清理会一直延后。

没有扫描证据时，只写 `staleDeferredAt` / `staleDeferredReason = scan_evidence_missing` 延后处理，**绝不永久拉黑**。这样修掉了原来的误杀链：对方已经回了 → 还没扫到 → 被 48h 拉黑 → 永远不再打开。

台账还有一条硬规则：**已完结的会话不允许被补发/误发回退**。已经写过 `chatClosedAt` / `round=3` 的目标，再调用破冰、广告、催加都不会把轮次打回 1，也不会清掉关闭时间；否则一次重复破冰就可能让同一个人再收一次广告。

## 七、租约启动不写“假运行”

关注/私信启动前要先向 OPS 申请舰队槽。申请期间状态只写 `leasing`，不写 `running`：

- 租约被拒 → 取消申请、释放槽，本拍不启动；
- 20 秒没回包 → 自动作废申请、释放槽，交回调度重试；
- 停止或取消后晚到的 token → 一律拒绝，不会再把模块拉起来。

这样不会出现“台账显示在跑、实际没跑、调度之后再也不启动”的静默停摆。

守箱模式还有一条独立保障：只要 `sg_run_mode=inbox` 且守箱开关打开，页面加载时就会自己挂上主巡航，不依赖出站开关 `dan_auto_run`。否则刷新一次页面，脉冲就再也不跑，表现同样是“全部无回复”。

## 八、反馈在哪里看

测试副本每个脉冲、每个会话都会上报 OPS：

- `chat.inbox_cycle`：这次是“守箱→拉新”还是“拉新→守箱”，带原因、是否已进列表扫描、查数间隔和基线人数。
- `chat.fan_roster_check`：每次回本号主页读粉丝数的结论（`first_scan` / `no_growth` / `growth` / `count_down` / `drain_ice` / `not_due` / `count_unreadable`），带本次读数、基线、差值和中文原因。
- `chat.inbox_pulse`：这一拍为什么没做事（没任务/导航中/列表空/白屏/超时/异常）。
- `chat.inbox_paused`：不在私信时段，守箱整体暂停；每小时最多一条，带 `chat_hours`（如 `09:00–18:00`）。
- `chat.inbox_tick`：这个会话为什么发/为什么没发（身份、回复原因、DOM 气泡数、发送失败原因）。
- `chat.stale_prune`：48h 清理这次清了多少、延后多少、为什么延后（`deferred_reason`）。
- 这些事件都带中文 `reason_zh`，不需要看代码猜。

关键反馈字段：

- `build`：这条事件来自哪个扩展版本（实际加载的 manifest 版本）。必须是 `4.9.45` 才说明新代码已生效；仍是旧版本就是扩展没重载。
- `test_24h`：测试副本是否为 24h 测试模式。4.9.12 默认 `true`，显式 `sg_test_24h=false` 才恢复 08:00–18:00。
- **OPS 台账轮次（必须按这个口径看）：** `1=破冰`、`2=广告或婉拒文案`、`3=首次催加（盾牌）`、`4=终催`。第二次催加必须单独写 `4`；如果复用 `3`，会被 OPS 的 `(bot,target,round)` 成功唯一键当成 `round_duplicate` 吞掉，台账就永远缺终催。婉拒在第 `2` 轮发文案后，再补一条第 `3` 轮的 `[age_reject_done]` / `[job_intent_reject_done]` 完结标记，OPS 才能把它标成“婉拒”而不是“广告”。
- `revived` / `revived_reason`：这条会话是不是“收口后又来信、重新进入判定”；原因会写清是精确未读、收口后入站时间、收口后回复时间，还是列表最后一条变成对方。硬拒绝/拉黑永不复活。
- `header_handle` / `header_source` / `header_confident`：这次会话头认成了谁、依据是什么、是否可信。`panel_header` 才是可信来源；`main_fallback` 只用于兜底，不单独阻断。
- `age` / `age_known` / `age_unknown_ad`：年龄读数、是否读出；读不出时照常发广告，但原因单独标出。
- `pending_draft`：列表最后一条是不是我方草稿（是则不算对方发言）。
- `scan_drop`：扫到但没有进入处理的会话数（被收口/冷却/草稿挡住时能看到）。
- `scan_drop.adWait`：已破冰、还在等回复，没到探测时间（非两段式的正常等待）。
- `scan_drop.kickWait`：广告或催加之后还没到下一次催加间隔。
- `pulse_seq`：这一拍是第几轮轮询（用该轮开始时间做编号）。
- `next_round`：这个会话的催加被“本轮已做过动作”挡住，要等下一轮。
- `wait_left_ms`：如果 OPS 额外配了时间下限，还差多少毫秒。
- `scan_drop_zh` / `scan_drop_samples`：同一批丢弃的中文明细，最多列 8 个 handles 和原因，直接看出是谁、为什么被跳过。
- `chat.inbox_non_text`：对方只发图片/贴纸/语音时单独成事件，带 `reason_zh`。
- `chat.inbox_task_abandoned`：发送重试被放弃的会话，带 `reason`（`retry_exhausted` / `pending_expired` / `pending_target_mismatch`）和 `tries`。
- `chat.stale_prune.deferred_reason`：48h 清理为什么只延后（如 `scan_evidence_missing`）。
- `chat.stale_prune.deferred_handles`：具体是哪些目标被延后（最多 10 个）。
- `scan_drop.noIce` / `no_ice_from_roster`：扫到但没破冰、守箱不处理的会话数（不是对方没回，是等拉新阶段破冰）。
- `scan_drop.unboundNoHandle` / `unbound_peer_no_handle`：列表里有会话、但既没有 @handle、peerId 也反查不到台账的“裸 peerId”。这种会话不能破冰、也不能发送，直接排除，不能占掉一整拍。
- `scan_drop.identityCooling` / `identity_unverifiable_cooling`：身份连续失败、正在冷却的会话数（不是对方没回，也不是被规则判死）。
- `chat.inbox_loop`：守箱心跳，每 60 秒一条。看 `hidden`、`busy`、`phase`、`last_pulse_at`、`next_pulse_in_ms`，就能区分“引擎停了”和“引擎在、还没到下一拍”。其中的 `ledger_pending` 直接列出最久没被处理的台账目标（round / kick / 是否收口 / 上次结论 / 多久没扫），用来回答“为什么这个人一直没轮到”。
- `reply_verdict` / `reply_verdict_zh`：每个打开的会话必须有的唯一结论（见 8.5）。
- `send_gate` / `send_gate_zh`：读到了回复但业务闸门不允许发时的具体原因（年龄、轮次、收口、时段等）。
- `hidden` / `activated_tab`：这一拍开始前标签是不是在后台、有没有成功激活。
- `scan_drop.renderFailedCooling`：连续 2 次读不到正文、正在 30 分钟冷却的会话数。
- `scan.latestUnreadHandle` / `scan.latestUnreadRank`：这一拍最先处理的未读会话与它在候选里的名次，用来核对“最新未读优先”。
- `last_speaker` / `preview`：这一拍选中的会话在列表里最后一条是谁说的（`peer` / `own` / `draft` / `unknown`）与预览文字。
- `ledger_replied`：台账历史上是否读到过回复；它不再单独决定打开会话，避免压过列表证据。
- `scan.scroll`：深度扫描的滚动证据。`steps` / `scrolledPx` 是实际滚了几步、多少像素；`rowsBefore` → `rowsAfter` / `uniqueRows` 是扫描前后的行数与去重后的总行数；`reachedBottom` 表示已到底；`stoppedReason` 为 `bottom_reached` / `scroll_not_moved` / `wheel_no_new_rows` / `no_scroll_container` / `deep_scan_throttled` 等。
- `scan.scroller`：真正被滚动的容器（`tag` / `testid` / `overflowY` / `scrollHeight` / `clientHeight` / `before` / `after`），用来核对是不是滚错了页面。
- `scan.lastSpeakerCounts`：这一拍候选里对方最后、我方最后、草稿、未知各多少，直接看出列表分层是否生效。
- `scan_drop.ownLastReplied`：列表最后一条是我方、视为已回复而没有打开的会话数。
- `scan_drop.unknownPreview`：列表读不到预览、且没有未读/到期动作而没有打开的会话数。
- `renderFailCount` / `renderFailAt` / `renderFailPreview` / `lastReplyVerdict`：台账里每个目标的渲染失败历史与最后一次结论。

判定原因有覆盖率测试兜底：`inbox-decision` 里每个结论都必须有中文解释；没登记的原因会显示成 `未登记原因：xxx`，不会再出现“只有英文代码、看不出错在哪”。

规则契约（`inbox-decision`）和运行时状态机（`inbox-state`）现在有逐项一致性测试：同一批场景下两边的动作、发的是哪条消息（route）、以及给出的原因（reason）都必须一致，避免“测试改对了、线上还是老逻辑”，也避免“动作一样但发成另一条消息”。

现场诊断命令 `inboxV2Diag` 还会返回 `cycle`（当前在守箱还是拉新、上次查数时间、下次到期、基线人数、当前读数）、`followUps`（待人工、身份连续卡住、48h 清理被延后的目标）、`scanDrop`（本拍丢弃明细）和 `pulseState`（脉冲是否在跑、下次时间、pending），排查时不用翻控制台。

浏览器本地 `sg_inbox_state.last` 也保留最后一拍结果，方便现场排查。

## 八点五、“打开会话”本身也必须可判定（4.9.4）

私信的所有“发/不发”都建立在“确实打开了这个人的会话”上。打开失败以前会被后续判定伪装成“对方没回”，现在必须区分开：

| 结论 | 含义 | 是否属于业务不回复 |
|---|---|---|
| `open_direct_nav` | 台账已有 peerId，正在按台账/列表行保存的会话地址直开，下一页继续 | 不是；技术处理 |
| `open_nav_failed` | 点击没能进入会话，已改为按地址直开 | 不是；技术处理 |
| `open_unreachable` | 既没有可直开的地址，也没有可点击的行 | 不是；技术异常 |
| `page_hidden_deferred` | 标签在后台，本拍不打开任何会话，20 秒后重试 | 不是；技术延后 |
| `reply_read_failed` | 会话已进入但读不到正文（0 气泡 / 0 文章） | 不是；技术失败 |
| `identity_pending` | 拿不到会话头，也拿不到可与台账核对的 peerId | 不是；“没证明是谁” |
| `header_handle_mismatch` | 会话头 handle 与目标不一致，已阻止发送 | 不是；疑似点错会话 |
| `peer_id_mismatch` | 会话 URL 的对方 ID 与台账不一致，已阻止发送 | 不是；疑似点错会话 |
| `ice_via_roster_only` | 台账没有破冰记录，守箱不补破冰 | 业务规则 |
| `await_reply` | 已破冰/已发广告，按规则等回复或等下一次轮询 | 业务规则 |
| `stage_closed` / `chat_closed` | 已按规则收口（婉拒、终催、拉黑等） | 业务规则 |

打开成功的判据是**真的进入会话路由并且会话已挂载**：路径必须已经带会话 id（`/i/chat/<id>`），并且读到消息气泡 / 读到会话头 / 输入框就绪三者任一。还停在 `/i/chat` 列表根时，输入框再明显也不能算打开。`pushState` 只改地址不重绘会被判成 `open_nav_failed`，随后按台账 peerId 直开，不会再进入“已打开但 0 条气泡”的假状态。

4.9.8 起，每次真正打开会话还会落一个唯一回复结论 `reply_verdict`：`reply_detected`（读到对方新文本）、`no_new_reply`（最后一条有证据证明是我方消息）、`reply_read_failed`（正文读不到，技术失败）、`identity_unproven`（有内容但没证明是谁）、`direction_unproven`（读到了气泡但无法证明最后一条属于哪一方）、`non_text_inbound`（只有图片/贴纸/语音）。如果读到了回复但业务闸门不允许发（年龄、轮次、收口、时段等），另记 `send_gate` / `send_gate_zh`，不把“读没读到”和“发不发”混成一个字段。OPS 不再只显示“没回复”。

**4.9.17 方向判定修正：** 气泡方向优先看左右位置，其次看发送者标签和已发话术；方向不明不再默认归为对方。若最后一条明确是对方但回复收集器漏字，会用该条文本补入回复检测。`chat.inbox_tick` 记录我方/对方/方向不明气泡数、最后一条方向和文本样本；方向不明时不发送，也不记成“对方没回”。

身份证明同理：只有“行自带 peerId 与 URL 一致”或“会话头等于目标 handle”才允许把 URL peerId 写回台账；否则只记 `identity_pending`，避免把 A 的 peerId 写到 B 名下造成台账串号。

## 八点六、4.9.8：后台标签页与渲染失败隔离

现场（2026-11-12 16:17–16:29）不是“没扫”：每拍 `rows=12 / scanned=12 / unread=1`，但打开后的会话 `dom_leaves=0 / dom_articles=0`，同时 `system.page_alive` 记录 `hidden=true`。Chrome 后台标签页里 X 不渲染会话正文，旧代码把它当成“已打开”，读不到气泡就整页刷新，刷新后又白屏，于是看起来像“对方一直没回”。

现在的处理：

1. **先激活标签再打开。** 标签是 `hidden` 时向后台发 `sg_activate_tab`，1.5 秒仍不可见再请求置前窗口；3 秒内仍不可见就整拍延后（`page_hidden_deferred`），不打开会话、不标已读、不写台账。
2. **打开必须有地址证据。** 优先点击列表行，让 X 自己走 SPA 路由；没有可点的行时才用会话地址直开。会话地址以列表行 href / 台账保存的地址为准——X 的会话 id 不保证“对方 id 在前”，现场既有 `<对方>-<本号>`，也有 `<本号>-<对方>`，不能靠顺序猜。还停在 `/i/chat` 列表根一律不算打开。
3. **不再整页刷新恢复空壳。** 读不到正文就落 `reply_read_failed`，同一目标连续 2 次进入 30 分钟冷却；未读也不能绕过冷却。列表预览文字变了（说明真来了新消息）会立即清零冷却并重试。
4. **失败后换目标。** 技术失败 5 秒后下一拍继续，90 秒内不重复同一失败目标；冷却中的目标进 `scan_drop.renderFailedCooling`，不会让整拍空手结束。
5. **顺序不变。** 同一优先级内按列表 DOM 顺序，X 按最近活跃排序，所以“最新未读”仍然最先处理；每拍 `scan.latestUnreadHandle` / `latestUnreadRank` 可以直接核对。

## 八点七、4.9.14–4.9.15：为什么“明明有回复却什么都没发生”

2026-11-12 19:39 的现场不是“对方没回”，而是链路在两个技术点断掉：

1. **整页跳转后 24h 测试被覆盖。** 脉冲按 peerId 直开 `/i/chat/<id>` 是整页导航，content script 会重新加载；`shared/config-sync.js` 随后按 OPS 的 `stagePolicy.test24h=false` 把 `sg_test_24h` 改回 false。19:47 已过私信时段，`runInboxModeTick` 在发心跳之前就返回，所以 OPS 上既没有 `inbox_loop` 也没有 `inbox_tick`。
   - 现在“私信测试”写 2 小时持久覆盖 `sg_manual_test_24h_until`，OPS 配置同步不清它；心跳提前到时段判断之前，并带 `paused_reason=outside_chat_hours`，能直接看出“引擎活着但被时段挡住”。
2. **扫描起点和打开地址不对。** 会话栏停在中段时只往下滑，会漏掉顶部最新会话；拼接地址又假设“对方 id 在前”，但现场有会话的行 href 是“本号 id 在前”，直开就白屏。
   - 现在深度扫描先回顶部再下滑；打开优先用行内 href，拼接地只做兜底；会话页白屏不再整页 reload，而是记 `blank_conversation`、回列表、给 `reply_read_failed`。
3. **自动翻译会伪装成“对方发言”。** X 把原文和中文译文分成两行，译文行没有“你:”前缀；旧逻辑取最后一行，就把“我方消息的译文”当成对方回复。
   - 现在中文“你:”算我方前缀，并识别“原文 + 译文”两行结构；只有原文没有我方前缀时才算对方最后发言。

判定优先级仍然是：**精确未读 → 视觉未读 → 对方最后发言 → 广告债 → 催加 → 探测**。先完整扫描列表到底，再从全量快照里找未读和对方最后发言；排序后每拍处理一个会话。`scan.complete=false` 表示没有扫到底，不能据此报告“信箱没有符合条件的消息”。普通收口后来信也会进入正文读取，硬拒绝/拉黑仍会被业务规则拦住。

## 八点八、4.9.27–4.9.30：引擎必须一直活着，积压必须连续排

2026-11-12 22:21 的现场问题是“引擎停了”，不是“规则判定不回复”：

1. 22:21:11 私信两阶段从 `watch` 切到 `roster` 后，OPS 只剩 `system.page_alive` / `system.sw_alive`，再也没有 `chat.inbox_loop` 或 `chat.inbox_pulse`。
2. 扩展上下文里 `content_chat.js` 的 `tick` 函数存在，但 `_sgChatMainEngineId=false`、`_matrixTimers=0`，说明文件加载成功、主循环 interval 没挂上。
3. 根因是文件末尾第二个 IIFE 里的看门狗和“私信测试”按钮直接调用了第一个 IIFE 的私有函数（`ensureChatMainEngine` / `loadInboxState` 等），每次都抛 `ReferenceError`，又被空 `catch` 吞掉。看门狗等于从未工作。
4. 4.9.27 在第一个 IIFE 末尾暴露 `window.__sgInboxApi`，第二个 IIFE 全部改走这个桥；同时在主引擎自己的作用域里增加 5 秒保活，`dan_auto_run=true` 或“守箱开且模式=inbox”时自动重新挂主循环。
5. 拉新阶段也必须有 `chat.inbox_loop` 心跳（带 `roster_reason / scan_active / count_tries / nav_tries`），不再出现“后台全空、不知道引擎死活”。

4.9.28 补齐吞吐：一次脉冲仍然只打开 1 个会话（避免同时操作多个页面状态），但如果扫描结果里还有多个待处理候选，下一拍改为 **8 秒后**继续，不再等满 60 秒。OPS 新增 `remaining_candidates` 与 `backlog_drain`，可直接核对“是不是在连续排水”。只有列表没有积压时才回到 60 秒巡检。

同时，`chat.inbox_tick` 增加台账阶段字段：`ledger_stage`（破冰/广告/第一次催加/第二次催加）、`ledger_round`、`ledger_ice_sent`、`ledger_ad_sent`、`ledger_kick_count`、`ledger_closed`、`ledger_closed_at`。看到 `send_gate=stage_closed` 时，能直接核对“是不是广告已发、两次催加都已发、会话已收口”，而不是只看到一个结论词。

4.9.29 再修一个顺序错误：后台标签页必须先激活，再判断“X 是否还在加载”。旧顺序把加载判断放在激活之前，Chrome 后台标签页只要还挂着一个 `progressbar`，每一拍都会返回 `page_loading_wait`，永远不激活、也不扫描。现场表现就是 `chat.inbox_loop` 有心跳、但一直没有 `chat.inbox_tick`。

4.9.30 修两处“看起来排了、实际永远轮不到”：

1. **revived 被选目标过滤。** `closed_inbound_queued_for_reply_check` 已经判定“收口后确有新入站”，但如果列表没有未读、预览又被识别成旧话术，`selectTarget` 会因为没有 `unread/peerLast` 信号把它再次丢掉。现在 `revived=true` 本身就是强信号，必定进入候选。
2. **打开失败冷却过长。** 连续 2 次打开失败原来冷却 30 分钟；后台标签页/白屏造成的失败会白白压住可回复会话。现在降到 10 分钟，并且 hidden → visible 时清空这层冷却，让被环境误伤的目标立即重试。

这两点解释了现场“扫到了、也排队了，但一直没 tick”的一类情况：不是业务不回复，是候选在选目标阶段被过滤，或目标还在打开失败冷却里。

判断“为什么不回复”时必须先看这三个字段，顺序不能反：

1. `reply_verdict`：有没有真正读到正文、读到的是谁。`reply_read_failed` / `identity_unproven` 是技术失败，不代表对方没回。
2. `send_gate`：读到了回复但业务闸门不允许发时的具体原因（年龄、轮次、收口、时段等）。
3. `reason`：这一拍本身在做什么（打开、回列表、等待、换目标）。

如果某个会话从未出现过 `chat.inbox_tick`，它的事实是“从未被成功打开”，不能解释成“规则判定不回复”。

4.9.46 补的是台账侧最后一个缺口：**本地已终催、OPS 只到第 3 轮**。此前两次催加都按第 3 轮上报，OPS 的唯一键把第二次当重复吞掉；修复后的新发送会写第 4 轮，但已经发过的人不会再有发送动作，所以历史缺口必须单独补。现在的规则：

- 只补“本地有发送证据、本地轮次高于 OPS、且没有补记成功过”的目标；
- 轮次口径固定 `1=破冰 / 2=广告或婉拒 / 3=首次催加 / 4=终催`；
- 补账不发消息，每 5 分钟最多 2 条，成功后写 `opsReconciledRound`，失败留待下轮；
- 心跳 `ops_ledger_pending` 表示还有几笔 OPS 缺账，归零才算台账完全对齐；
- 没有本地发送证据的台账，不会被 OPS 反向造账（避免把历史线索灌成假广告/假催加债）。

4.9.47 修掉拉新阶段的一个“假查数”：读粉丝数前要求当前页是本号主页，旧判据只看 `getMyHandle()`；导航栏没渲染或只拿到 worker id 时会判成“不是本号主页”，直接返回 0，被记成 `count_unreadable`，整轮拉新等于没做。现在改为 `my || 导航栏本号链接` 任一与路径一致即可，并允许“路径 handle = 粉丝链接 handle”自证；`chat.fan_roster_check.read_detail` 会带 `my / nav_handle / path / is_profile / links / best / reject`，读不到时能明确是没进主页、没找到链接，还是 handle 对不上。

4.9.48 起 `chat.inbox_loop` 心跳带 `heap_mb / dom_nodes / timers`。这三项是矩阵化前的单页基线：Chrome 内容脚本拿不到进程级 CPU，但可以用 JS 堆、DOM 规模、定时器数和 `system.pressure.lag` 组合判断“多开多少页会开始拖慢”。它们只读，不参与任何发送判定。

4.9.49 补上一条硬约束：**广告和催加必须带可点击的推广链**。旧逻辑在推广链还没同步到本页时，催加分支仍会返回模板原文，现场出现“广告/催加发出了，但对方没有任何入口”。现在模板既无 `{LINK}`、也不含 `line.me`、且当前无链时直接不发，`chat.inbox_tick.send_error=no_promo_link`，并带中文 `send_error_zh`。这属于配置/同步未就绪，不是对方没回。

4.9.57 修的是“明明有回复却一直不处理”的三个直接原因：

1. **会话行 ID 解析错，打开的不是台账目标。** 新版搜索结果行有时只有一段 `row.id`，两段 ID 在 `href` 里。旧逻辑只把 `row.id` 的第一段当对方，导致把本号或错误的人写进台账，后续必然 `peer_id_mismatch`。现在单段 ID 会从 `href` 补齐两段，再用本号 ID 反推对方；两段都不等于本号时明确判 `unresolved`，不再猜。
2. **真实回复被后面的广告/催加遮住。** 旧收集器只取“最后一条我方气泡之后的对方文本”。会话一旦变成「破冰 → 对方回复 → 我方广告 → 我方两次催加」，对方那句回复就永远读不到。现在改为收集**破冰气泡之后的全部对方文本**，再用回复指纹去重：同一批文本只执行一次动作，发送失败不写指纹，下一拍还能重试。
3. **会话页没有真正滑到底/没有回翻历史。** X 的消息列表是虚拟滚动，旧滚动函数只认几个固定 testid，找不到就停在旧位置；破冰气泡如果在更上面，按边界收集会得到 0 条。现在从消息区向上寻找真实滚动祖先，等待渲染时持续贴底；读取前最多向上回翻 4 次寻找破冰文案，再回到底部。OPS 新增 `history_scroll` / `history_scroll_zh`，能直接看到“回翻了几次、有没有找到破冰、有没有加载到更多历史”。

另外补了打开后的地址核对：候选行的 `peerId/href` 与实际打开 URL 不一致时，本拍记 `open_target_mismatch`，**不读回复、不写台账、不发送**，并立即换下一个目标。这条不是“对方没回”，而是“打开错人已被拦住”。

判断一个会话为什么没动作，仍按这个顺序看：

1. `history_scroll`：有没有回翻历史、破冰边界是否找到；
2. `reply_verdict`：正文是否读到、读到的是谁；`reply_read_failed` / `identity_unproven` 是技术失败；
3. `peer_text_unchanged` / `peer_hash`：这批回复是不是已经处理过；
4. `send_gate`：业务闸门（年龄、轮次、收口、时段）；
5. `reason`：这一拍本身在做什么（打开、换目标、等待、发送）。

## 八点九、4.9.116：脉冲“看起来在跑、实际什么都没扫”

2026-11-13 14:02 之后 OPS 只剩 `system.sw_alive`，`chat.inbox_*` 一条都没有。
查下来是三个互相独立的真问题，任何一个都会让“有没有回复”这个问题失去意义。

### 1. X 页面消失 → 引擎彻底停摆

后台每 60 秒的存活检查只处理“已经存在的 X 标签”；标签一个都不剩时直接空转。
后台 keepalive 还在写存活事件，所以 OPS 看起来“插件在跑”，
实际上内容脚本已经全部不存在。

现在：后台每分钟检查一次；**没有任何 X 标签**且守箱开着 → 自动补一个后台 X 页
（`active:false` 不抢焦点），3 分钟最小间隔、每小时最多 4 次。
守箱开关通过 `sg_inbox_watch_on` 同步到扩展存储，后台才判断得了。

### 2. 用过期缓存判“没有任务”

后台标签页为了不抢焦点，先用整箱快照预检。旧逻辑只要候选为 0 就 `no_task` 并跳过激活，
不看缓存有多旧。13:58 那拍用的就是 4.5 分钟前的快照，报 `peer_last=0`，
而同一份列表 4 分钟前有 16 条“对方最后发言”。

现在：缓存超过「一拍 + 30 秒」（90 秒～5 分钟）即作废，强制激活做真扫描，
OPS 记 `cache_stale_forced_scan`。**过期快照不再有资格否定真实回复。**

### 3. 终催复用首次催加原句

约会池三套话术在 OPS 里只有 `kick_message`，没有 `final_kick_message`，
旧兜底链直接退回同一句，7 个人连收两遍一模一样的催加。
现在终催优先取终催文案；若最终结果与首次催加完全相同，强制改用默认终催文案。

### 排查顺序（新增两条）

1. `system.sw_alive` 有、`chat.inbox_*` 没有 → 先看有没有 X 标签（引擎是否还在页面里）；
2. `action=idle / reason=no_task` 且 `cache_age_ms` 很大 → 缓存过期，本拍结论不可信。
